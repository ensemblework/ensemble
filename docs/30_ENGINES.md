# 30 · Engines: who does the work, and how their questions reach you

A code task is done by one of:

- **Ensemble's agent**: Ensemble's own tool loop calling a model with the selected credential or funding source (`apps/hub-api/src/workspace/agent.ts`).
- **Claude Code**, **Codex**, **Cursor's agent**, **GitHub Copilot**, **Grok Build**, **OpenCode**, **Gemini CLI**, **Google Antigravity**, **Mistral Vibe**, **Qwen Code** or **Kimi Code** on the person's computer, signed in with their own account (§1–§3).
- **The agent's own app or a terminal**: the Claude app, Codex in the ChatGPT app, Cursor or VS Code; or Claude Code, Codex, Cursor's agent or Copilot CLI in a terminal window (§4).

The Assign dialog's agent picker picks one (or Auto: the agent Settings → Models names for the task's complexity); run profiles remember it. When Ensemble runs the task, the same run settings apply: mode (Ask, Review only, Run unattended), folder trust, sandbox, outside-folder access, git permission, internet and limits ([24](24_DESKTOP_SANDBOXING.md), [06](06_MODULE_WORKSPACE_AND_SURFACES.md)). In an agent's own app, that app's settings apply. A hosted Ensemble runs Claude Code, Codex, Cursor and GitHub Copilot tasks only on a paired computer.

Paths below are under `apps/hub-api/src/` unless qualified.

**From the terminal.** The `ensemble` app ([26](26_CLI.md)) starts the same runs: `/run <what to do>` creates a task and assigns it to the agent chosen with `/agent`, in the folder the app was opened in, under the profile chosen with `/profile` (`runRequest` in `apps/cli/src/tui/model.ts`).

**Chat with your own agent.** With Claude Code, Codex, Cursor's agent, GitHub Copilot, Grok Build, OpenCode, Gemini CLI, Antigravity, Mistral Vibe, Qwen Code or Kimi Code chosen, the app's Chat tab is that agent. Each message is a run with `chat: true` (`Assign.chat`, kept on the job's context; refused for Ensemble's agent), so every run rule applies.

- The first message says where the agent is (the terminal chat, the folder), the ensemble MCP tools and how the run works (`engineRules`). Later messages continue the run (`continueFromJobId`) and resume the agent's session from its `engine` event (`claude -p … --resume <session>`, Codex `thread/resume`, Cursor's and Copilot's `session/load`, whose replayed history is not part of the reply), and are sent as typed; the rules go again only when the person changed the run's settings since the last message (`chat_rules` event, `rulesHash`; `chatPrompt` in `workspace/agent.ts`).
- If the session cannot be reopened (`SessionGoneError`: deleted, or made on another computer) or the agent changes mid-chat, the message runs in a new session with the previous turn's summary.
- An assistant or node conversation on an AI plan (§8) whose session was deleted in the agent goes on in a new session that gets the instructions and the conversation so far. Copilot's `--session-id` would quietly start an empty session under the deleted one's id, so its session is looked up in Copilot's own `session-state` first (`copilotHasSession`); the other agents refuse to reopen one they no longer have.
- The chat's task stays In progress and gets no Agent report per turn.
- The run's MCP server (`scripts/ensemble-ask-mcp.mjs`, `ENSEMBLE_CHAT=1`) adds `ensemble_list_tasks`, `ensemble_create_task` (owner "me"; text goes on the task's page) and `ensemble_search` (notes, pages, tasks, meetings) to `ask_person`, answered by `POST /api/engine/tool` on loopback with the run's secret, chat runs only (`workspace/engines/chat-tools.ts`). The judge passes them without a prompt, as they touch only the person's own board.

**Agent sessions** (`workspace/sessions.ts`). A session is one conversation with a coding agent (Claude Code, Codex, Cursor's agent, GitHub Copilot, Grok Build, OpenCode, Gemini CLI, Antigravity), carried across the runs that continue each other (`continueFromJobId`) with the same agent. It is derived from the runs, not stored: its id is its first run's id, its agent session is the newest `engine` event in it, and the chain's resource key keeps it to one turn at a time.

- Continuing a task in a session (Assign's "Continue an earlier task", the assistant's `session`, `Assign.session`) resumes the agent's own conversation (`earlierSession` walks back to the nearest recorded session) and sends the new task with a line saying it continues there (`sessionTaskPrompt`); the agent keeps what it learned and its prompt cache. A session that cannot be reopened (`SessionGoneError`) runs as a new one with the full prompt.
- **A session that no longer exists.** The person may delete a session in the agent's own app, or the agent may expire it (Claude Code after 30 days). Every agent says so when asked to reopen it (Claude Code: "No conversation found", exit 1; Codex: "no rollout found for thread id"; Copilot, Cursor and the ACP agents: `session/load` refused), and the run goes on in a new session in the same folder with the full brief, which has the earlier task's title, outcome and summary ("This continues an earlier task"). Every agent keeps a session's id when it resumes it, so the web tells a resumed run from a restarted one by the ids computers already send (`sessionRestartOf` in `workspace/session-continuity.ts`): the task page says the earlier session no longer existed, the run's `SessionChoice.outcome.resumed` is false, and a node is told in its run note that the agent did not remember the earlier conversation.
- **A session deleted in Ensemble** (by the person, a node, or the clean-up) is not reopened at all (`sessionToResume`): a run continuing one of its runs ("Continue an earlier task" lists them as "its agent session was deleted: a new one starts there") works in that folder in a session of its own (`continuesSessionOf` in `workspace/sessions.ts`), which is listed, chosen and cleaned up like any other; the deleted session keeps only its own runs.
- A run that continues a run in a folder the person granted (a shared folder) works in that folder however long the chain, since only the first run carries the grant (`grantedFolderOf` in `workspace/agent.ts`).
- `Assign.session` (any run id in it) runs on the session's computer, under its current pairing, in its folder, with its agent, model, thinking level, context window and fast mode unless others are named (a run profile's do not apply); another agent or computer is refused. Each setting is kept, reset to the agent's own default (`"default"`, or `fast: false`), or set as named, separately (`sessionChoices` in `workspace/assign.ts`): naming a model keeps the thinking level and context window. The task's model tier adds nothing to a run in a session.
- `GET /api/agent/sessions?taskId=&deviceId=&q=&limit=` lists the person's sessions, newest first, each with agent, model, computer, folder, first and latest task, a one-line summary of the latest report, status (`working`, `waiting`, `queued`, `idle`) and whether it can be resumed; `GET /api/agent/sessions/:id` reads one, and a job's detail carries its `session`. The web shows no session list.
- Ensemble Node's nodes start and drive sessions, each node only its own ([35 §8](35_ENSEMBLE_NODE.md#8-work-on-a-computer)). A **steer** is a run that continues the one it interrupts, with `context.steer {update}` (the claim spec's `steer` on a paired computer); resuming the session, the agent gets only the change (`steerPrompt`), and with the session gone it gets the whole brief with the update in its instructions.

**Agent projects** (`workspace/agent-projects.ts`). The person's own agents keep their sessions by working folder (Claude Code's projects, Codex's and Cursor's workspaces, Copilot's sessions by folder), so an Ensemble project gets one folder for its tasks: `<workspace>/projects/<name>`. A task in a project that the person's own agent does, and that would otherwise get a new folder (no earlier task continued, no folder, repository, chat or Ensemble Node plan), works there, and the agent's app lists it with the project's other work. The folder is a git repository like a run's own; runs in it take turns (the `dir:` resource key, and the queue's same-project rule). Session lists (the Sessions page, Continue an earlier task, `ensemble sessions`) show such a session's folder as `projects/<name>`, from the folder its computer reported for the run (the `prepared` event); a run in a folder of its own shows "its own checkout".

- The project's brief (name, summary, notes, project page, repositories, people and their roles, upcoming deliverables) is Markdown with a hash (`projectBrief`). The web server builds it when a computer claims the run (the claim's `project`, [25](25_REMOTE_TASKS_ON_YOUR_COMPUTER.md)); a local-only computer builds it from its own database. Older computers ignore it and use a new folder as before.
- Before the agent starts, the brief goes into the folder's `AGENTS.md` between Ensemble's markers (the rest of the file is the folder's own), with `CLAUDE.md` and `GEMINI.md` importing it (`@AGENTS.md`), only when the hash differs from the one last written there. Those three files are kept out of the repository (`.git/info/exclude`). Runs in the folder can change them, so Ensemble never reads or writes them through a link: it reads a plain file only (`O_NOFOLLOW`) and writes a new file renamed over the old one. A continued run in the folder gets the same check (`bringProject` in `workspace/agent.ts`).
- The run's rules say it is the project's folder, that `AGENTS.md` has the brief (and, when the project changed since the folder's last run, to read it again), and to keep files only this task needs in a folder named for it. Codex, Copilot, Cursor and OpenCode read `AGENTS.md` themselves; headless Claude Code reads only the person's own settings in an Ensemble folder (a run could otherwise plant hooks for the next one), so its brief comes through the prompt's context and the rule, and `CLAUDE.md` is for the person opening the folder in the Claude app.
- Which folder is which project's, and the hash of the brief each last got, is kept in `projects/.ensemble-projects.json`, beside the folders and outside any of them, so nothing a run writes in a project folder can point Ensemble at another. A renamed project keeps its folder (and its agents' sessions); one removed is made again under its name; another project with the same name gets its short id after the name. Opening a project's task in the agent's own app (§4) opens the project's folder too.
- Off with Settings → Agents → Agent sessions → *One folder per project* (`orchestration.projectFolders`). Apps' own "Projects" (claude.ai, ChatGPT) have no API an agent run can use; the working folder is what the coding agents group by.

**Choosing a session** (`workspace/session-choice/`). A new run by the person's own agent that would start a new session in a new folder (no `session`, `continueFromJobId`, folder, repository, pull request or chat; not an Ensemble Node plan or a retry) may continue one of the agent's sessions that fits the task. No model takes part: the same records always give the same decision, in milliseconds.

- **Where.** On the computer that runs the agent, when it takes the job (`createJob` in its runtime, `mayChoose`): its sessions and the text of its earlier runs are there. Ensemble on the web sends with each claim what the computer cannot know (`related`: the task's project, deliverable, meeting, parent page, labels and the tasks it names, `factsOf`; `sessionChoice`: the config, with the person's setting in `enabled`; `newSession`). A local-only computer has the records itself. The computer keeps each claimed task's facts on its run (`context.taskFacts`), so later runs are matched against it. A run claimed before 0.7.4 has none and is never a candidate.
- **Candidates.** This computer's sessions of the same agent that are idle, resumable, not chats, not being deleted, active in the last `limits.maxAgeDays` (30, as agents keep them), at most `limits.candidates` (20), newest first, and whose every task is of the same space and account as the new task (the web space a claim came from and whom it runs for there, `related.space` and `related.runner`; this computer's own tasks are a space of their own) and in its project, or all in none: sessions never cross spaces or projects.
- **Signals** (`Signals` in `score.ts`), for each candidate against the new task:
  - *link*: the task names a task of the session: an @mention on its page, a link in its text or the run's instructions (`ensemble://task/<id>`, `/tasks/<id>`), or a dependency;
  - *deliverable*, *meeting*, *parent page*: the same one as a task of the session;
  - *anchors*: exact things both name (`anchorsOf` in `text.ts`): file paths (a file shared by its path is not counted again by its name), code names (`rankResults`, `auth_session`, `SessionStore`), issue and pull request numbers (`#123`, `ABC-42`), web addresses. The session's side includes the files its runs changed. An anchor in more than `limits.anchorMaxDocShare` (20%) of the person's tasks, shared with more than half of the candidates, or a file every repository has (`package.json`, `README.md`, `index.ts`…) does not count;
  - *topic* (0–1): the cosine of TF-IDF vectors. Words are lower-cased, common English words and `text.extraStopwords` dropped, reduced to their stem by Porter's algorithm (ranking, ranked, ranks → rank), and each two neighbours also count as a phrase (1.5×). A term weighs (1 + ln count) × ln((N+1)/(df+1)) over the person's last `limits.corpusTasks` (2,000) tasks on this computer, so words in nearly every task weigh about nothing. The title counts 3×, labels 2×, the page, description, run reports and instructions 1×. It counts only with at least `limits.topicMinShared` (2) shared terms that are not common, and proportionally less while the person has fewer than `limits.minCorpus` (50) tasks;
  - *follow-up* or *new work*: the new task's title (`text.followUp`, `text.newWork` patterns) or labels (`text.followUpLabels`);
  - *warm*: the session was active in the last `warmMinutes` (60), so the provider's prompt cache is likely still there. Not a cut-off: a session days old is continued as readily, at the cost of the agent reading its conversation once uncached;
  - *fill*: how much of its context window the session uses, from its agent's last report (`engine_context` `used`/`size`: Claude Code's and Codex's last request, Copilot's and the ACP agents' own figure), and *tasks* in it.
- **Score** (`scoreCandidate`): the sum of weight × signal. Defaults: link 10, deliverable 3, meeting 3, parent page 2, 3 per anchor up to 6, topic × 6, follow-up +1, new work −1 (only when no link or anchor ties it), warm +1, filling more than `size.soft` (40%) −2, unknown fill and more than `size.longChainTasks` (8) tasks −2. More than `size.hard` (70%) full, or unknown fill and more than `size.hardChainTasks` (15) tasks, is too full to continue: each more task re-sends the whole conversation on every request, cached or not, and near its window the agent compacts it and loses detail.
- **Bands** (`decide`): the best score (then the most recently active) at or above `bands.confident` (6) is continued, silently: the run's card on the task page says which session and why ("Continued the agent's session: it mentions “Build the ranking API”"). When the best confident ones are too full, a new session gets the best one's last report in its instructions instead. At or above `bands.unsure` (3), and below 3, a new session, recorded with its band so near misses can be studied. Nothing asks the person: Assign → More options → *Always start a new agent session* (`Assign.newSession`, the assistant's `newSession`) skips it for a run, and Settings → Agents → Agent sessions → *Continue a fitting agent session* (`orchestration.linkedSessions`) turns it off.
- **Cost.** Bounded by the limits above: the rarity table is built from titles, labels and the first part of descriptions and pages, kept per account for `limits.corpusTtlMinutes` (60), and word matching stops at `limits.timeBudgetMs` (3 s), after which links and structure decide alone. A decision with 20 candidates takes tens to a few hundred milliseconds.
- **Tuning** (`config.ts`, `SessionChoiceConfig`). Every number and word list above is one versioned config with its defaults in code. On the web server, `ENSEMBLE_SESSION_CHOICE_CONFIG` names a JSON file with only the fields to change (for example `{"version": "2026-12-01.1", "weights": {"topic": 8}, "bands": {"confident": 7}}`); it is checked, read again within a minute of a change, and sent with every claim, so computers decide with it from their next run without a release. An invalid file is logged and the defaults apply. A local-only computer reads the same variable on itself. Change `version` with every change.
- **Records** (`SessionChoice`, table `session_choices`). Every decision: the run, task, agent, computer and project, `decision` (continue or new), `band`, the session continued or the best candidate, its score and reason, `note` (`new-session`: asked for; `too-full`; `unavailable`: the session could not take the run; `not-linked`: the web refused the session the computer named), `configVersion` and `configHash`, and every candidate's `signals`, `parts` and score, best first. When the run ends, `outcome`: its status, duration, tokens, and for a continued session whether the agent really resumed it (the agent's session id stayed the same). A computer keeps the record and sends it to the web in the web's ids (`POST /api/devices/self/jobs/:id/session-choice`, under the job's lease), which links the run to the session it continued (only one of the same account and agent on that computer). Kept for the history window (`historyRetentionDays`). To calibrate, read the rows (bands near the thresholds, `note = 'new-session'`, `outcome->>'resumed'`) and score their stored `signals` again under other weights with `scoreCandidate`: no text is needed.

**Cleaning up sessions** (`workspace/session-cleanup.ts`). The scheduler sweeps each account every 15 minutes (`orchestration.cleanSessions`, on by default): a session goes from its agent (`deleteAgentSession`, ledgered as `workspace.session.delete` by `system` with `reason: "retired"`) once every task in it is retired: deleted at least 10 minutes ago (so Undo still finds it), or done or dropped longer than the completed window and not pinned. A session with a run still queued or going waits for the next sweep; one with a task still in use is looked at again after 6 hours, and one on a computer that is offline or too old to delete sessions after an hour (`context.sessionCleanup.nextAt` on its runs), so it never holds up the sessions behind it. A failed deletion is tried again a day later. Each sweep reads a session once, however many of its runs match, looks at no more than 60 and deletes at most 20. Just before anything changes, under the session's lock, the deletion checks again that the session has the same runs, none of them going, and every task still retired (`guard` of `deleteAgentSession`); otherwise it leaves the session alone. Ensemble's run records, project folders and files stay. A computer deletes the sessions of its own local tasks itself and leaves those of runs claimed from the web to the web. An assistant chat's agent session that has gone unused for 30 days is deleted from the agent too, with its folder (`subscriptions/turn-sessions.ts`). A coding session an Ensemble Node started for itself (its task's `sourceRef` is `node:<id>`, which stays open) goes once none of its runs started or finished in 7 days (`NODE_SESSION_IDLE_DAYS`, `ENSEMBLE_NODE_SESSION_IDLE_DAYS`), with the same lock and checks; a person's own open task still keeps its session.

**Ensemble Code.** With Ensemble's agent chosen, the Chat tab is Ensemble Code: the assistant with a code session (`assistant/tools/code.ts`). It reads, lists and searches the folder and reads PDF and Office files as text. Its one write, `ensemble_start_agent`, creates a task and starts the chosen engine on it with the profile's settings (or in a fresh clone when given a repository URL) through `createJob`, so every run rule applies. It follows the assistant's write policy ([11 §6](11_HOW_THE_ASSISTANT_WORKS.md#6-apply-undo-and-dependent-actions)); applied from a proposal it is ledgered as `assistant.ensemble_start_agent`. Ensemble Code never edits files or runs commands itself, and the hosted API refuses it (409): it needs the runtime on the person's computer.

## 1. Claude Code as the engine

**Account boundary.** Ensemble starts the person's own unmodified `claude` with its own sign-in: the `claude` command on the trusted PATH (never inside the work folder; the PATH comes from the login shell and usual install folders such as `~/.local/bin`), else the Claude app's copy (§8; `claudeBinary` in `subscriptions/detect.ts`). Ensemble never offers a Claude login, reads Claude credentials or runs Claude Code on its servers; API-key variables are removed (§6).

**A run** (`workspace/engines/claude-code.ts`):

1. Ensemble prepares the folder, branch and trust as for its own agent.
2. It starts `claude -p <task> --output-format stream-json --verbose --permission-mode default --setting-sources <sources> --settings <per-run JSON> --mcp-config <per-run JSON> --max-turns <limit> [--model <model>] [--effort <level>]` in the work folder. Model, thinking level and context window go through `claudeLaunch` (`packages/shared-types/src/claude-models.ts`): the long window is the model id with `[1m]` (`claude-sonnet-4-6[1m]`), and each level is sent under the name that model takes (Opus 4.7's Extra high is `max`). A level or window the model does not take is left out with an `engine_note` on the run. `<sources>` is `user,project,local` in a folder the person trusted themselves, by name (a saved trust rule for that very folder, for good or for this task; `exactTrust`, `engineTrust` in `engines/registry.ts`), so the repository's own `.claude/` settings and hooks load as in their own Claude Code. Anywhere else, including folders inside a trusted one, the workspace and fresh clones, it is `user`, and they do not run.
3. The per-run settings add a **PreToolUse hook on every tool** (`scripts/ensemble-hook.mjs --engine`). It sends the call to `POST /api/engine/ask` on this computer with the run's secret, and Claude Code waits for the answer from the judge (`workspace/engines/judge.ts`):
   - **Inside the folder.** Edits and commands follow the mode: allowed in Review only and Run unattended; asked on Needs me in Ask unless the folder is trusted. A Bash command that only reads files in the folder runs without asking in every mode, as the person's own Claude Code, Codex and Copilot run it (`quietCommand` in `engines/judge.ts`; `quietRead` and `quietArgs` in `workspace/tools.ts`, also used by Ensemble's agent). Every program in it reads only (`ls`, `cat`, `grep`, `rg`, `find` without `-exec`/`-delete`/`-fprint`, `wc`, read-only `git status|log|diff|show`…); every name it reads, followed through links, and every match of its globs is in the folder; it runs in the folder, redirects only to device files, and has no `VAR=value` or `env` in front. Still following the mode: variables, `$(…)`, backticks and brace lists; pagers and tools that read a project config that can set one (`less`, `bat`, `ack`); `sed` and `curl`; options that start a program, write a file or follow links (`rg --pre`, `fd -x`, `sort -o`, `git diff --output`, `grep -R`, `diff -r`); git options before the subcommand; PowerShell and Windows. Read-only git also needs the sandbox and a repository config without a pager, diff or filter driver, fsmonitor or include.
   - **Outside the folder.** The zones and `outsideAccess` rules of [24 §3](24_DESKTOP_SANDBOXING.md#3-work-folder-and-outside-access) decide, for Ensemble's agent and every engine (`outsidePath` in `workspace/tools.ts`): reading goes ahead; Run unattended changes other folders in the workspace and the person's own folders; Review only and Ask ask once per folder before changing it, then work there freely for the run. A shell command is read the way a shell reads it (`workspace/shell-parse.ts`): quotes first, `cd` sets the folder later relative paths resolve in, redirects (`>`, `>>`) are writes, and code passed with `-e`, `-c` or `--eval`, a search pattern, a URL or `/dev/null` is not a path; a program writes unless it only reads (`readsOnly`). Claude Code's sandbox gets matching paths (`claudeFilesystem`, `engineSandboxPaths`). Keys, sign-ins and browser data (`SECRET_PATHS` in `workspace/guard.ts`), another account's files, Ensemble's own data and its git helper are always refused; start-up files (`.bashrc`, `.zshrc`, `.gitconfig`, launch agents), system folders and Ensemble's own code are refused for writes (`outsideRefusal`). The agents' own skill folders (§10) are read in every mode, and a skill's script run there is a read of that folder, not a change (`skillScript` in `engines/skills.ts`); a write there is judged like any outside folder. With No access, Claude Code's sandbox opens them for reading too.
   - **Git and GitHub** have no limits of Ensemble's own (`checkGit`): with No limits the engine commits, makes and switches branches, pushes any branch (force and deletes included) and opens, comments on or merges pull requests with `gh`, using the computer's own sign-in, approved like any command by the run's mode. Only the person's choices stop it: Local only refuses commits, merges, rebases and the like; Commit refuses pushes; "Ask me before each commit" asks each time; internet off refuses network git and `gh`. With a pull request plan, Ensemble also pushes, opens and merges it as the task says, for every engine ([24 §5.1](24_DESKTOP_SANDBOXING.md#51-pull-requests)). With Local only, a commit made some other way (a script) is undone at the end; the files stay.
   - **`git clone` with the sandbox on is done by Ensemble.** Claude Code's sandbox blocks writes to `.git/config` and `.git/hooks` under the run folder (so a clone there fails), and loosening that would let a script plant a hook that runs unsandboxed later. For `git clone <https URL> [folder]` alone or first in a chain, the judge clones itself (`cloneForAgent` in `workspace/tools.ts`, rules in `workspace/clone.ts`) and tells Claude Code where the repository is. Only a public `https` URL without user name, query or port; no credentials or hooks (`--template=`; `file://` refused); into a new folder in the run folder, under Ensemble's sandbox with internet on. Kept flags: `--depth`, `--branch`, `--single-branch`, `--filter`, `--no-tags`, `--quiet`. The clone's `.git/config` and hooks stay read-only. A clone after other commands (`cd x && git clone …`) is refused with the reason. Files that can run code later (`folderOpen` task, `.envrc`, husky hooks, install scripts, Makefile) are flagged in the answer and run summary. With the sandbox off, Claude Code's git runs as usual. Ensemble's agent uses the same function; Codex and Cursor keep their own handling (their approval answers carry no message). A task can also name a repository at assignment (`repoUrl`), cloned as the run folder.
   - Privilege, persistence, keychain and machine-control programs (`sudo`, `crontab`, `launchctl`, `security`, `osascript`, `pkill`, `shutdown`, …; `isNeverProgram`) are refused. Programs that reach another computer (`ssh`, `scp`, `sftp`, `nc`; `isRemoteProgram`) need the internet and ask in Ask and Review only. Developer tools such as `docker`, `nohup`, `tmux` and `kill <pid>` follow the mode. With internet off, web tools are refused.
   - A refusal goes back to Claude Code with the reason, and it carries on.
4. **Questions.** Headless Claude Code has no question tool, so the run adds Ensemble's **`ask_person`** (MCP server `scripts/ensemble-ask-mcp.mjs`). It shows the question on Needs me with options, the recommended one and a free-text box; the call waits for the answer (app, web, phone or `ensemble needs`). Each engine gives this server a day-long tool timeout, as long as the card lasts (Claude Code `MCP_TOOL_TIMEOUT`, Codex `tool_timeout_sec`, Copilot the server's `timeout`: its default is 180 s, after which the agent got "Request timed out" and gave up). While it waits the server sends MCP progress notifications when the call carries a progress token. If the agent still stops waiting (`notifications/cancelled`), the server hangs up and the card is withdrawn (expired), here and on the web (`/api/devices/self/decisions/:id/close` with `expired`), since an answer would reach nobody. In Run unattended it returns the recommended option at once, and every such decision is listed on the task. A task run's server also has `report_result` and `attach_evidence` (§9). Agents that ask their own questions are asked the same way: Claude Code's `AskUserQuestion`, Codex's `item/tool/requestUserInput`, Cursor's `cursor/ask_question`, and a form an agent or an MCP server inside it sends (ACP's `elicitation/create`, OpenCode's question tool; an MCP server's form through Codex): each field is one question with its choices (`answerForm` in `engines/elicitation.ts`), unattended runs take the field's default or first choice, and a form asking for a password, key or token is declined.
5. **Sandbox.** With the sandbox on, Claude Code's own sandbox (Anthropic's sandbox-runtime: Seatbelt on macOS, bubblewrap on Linux) confines shell commands to the work folder, the cache and the folders the run was let into (Run unattended: also the workspace's folders and the person's own folders). A command it stops may be retried outside the sandbox (`dangerouslyDisableSandbox`); the hook judges that retry: allowed in Run unattended, in Review only when its outside paths are all in allowed folders, otherwise asked. Where it cannot run (native Windows; Linux without bubblewrap and socat) Claude Code does not start; Ensemble says so and the sandbox can be turned off for the run. Internet off is an empty domain list.
6. **Progress and trace.** The stream (`system/init`, `assistant`, `user`, `result`) feeds progress, live log, tool count, tokens and reported cost, and the run's trace (`EngineTrace`, `workspace/engines/trace.ts`): thinking, messages, and each tool call as one step (name, summary, input, then output and duration from its `tool_result`; failed if marked an error), in the engine's order. Previews only (`TRACE_PREVIEW`): input 600 characters, output 1,200, thinking and messages 2,000, final answer 20,000; at most 600 steps. Secrets are redacted by shape (`lib/redact.ts`), and a call reading a secrets file (`.env*`, private keys, `.npmrc`, `.netrc`, credentials files) gets no output. Open calls end when the run stops or fails. The Runs page shows the trace ([02](02_MODULE_INTERACTION_HUB_UI.md)); a paired computer sends the same previews to the web ([25](25_REMOTE_TASKS_ON_YOUR_COMPUTER.md)). The final reply is the task summary; model, cost estimate and changed files (names, line counts) are kept on the job (`evidence`).

A task assigned on the web with Claude Code runs the same way on the paired computer; its Needs me cards reach the web and phone through it ([25](25_REMOTE_TASKS_ON_YOUR_COMPUTER.md)). **Models:** the ones Claude Code itself lists for the plan (§8: its `initialize` reply, each with its thinking levels and whether it has fast mode), with each model's context window and default level from `CLAUDE_MODELS` (`claude-models.ts`: a fixed 1M or 200K, or 200K with a 1M choice; aliases `opus`, `sonnet`, `haiku` and `fable` follow the newest of each), then the earlier models that version still runs (`minVersion`). Before the computer reports, the table stands in. The table follows T3 Code's model manifest (MIT). **Fast mode:** the per-run settings carry `fastMode: true` for a model that has it; one without it runs at its usual speed with an `engine_note`.

   - `config.mcp_servers.ensemble`: the same `ask_person` server with the run's secret.
   - `turn/start` carries the run's thinking level as `effort`, checked as for Claude Code, and with fast mode the model's fast service tier as `serviceTier` (from `model/list`: the tier named Fast, `priority`, else the `fast` speed tier; `codexFastTier`).
2. Codex's requests are answered by the same judge (`answerCodex`):
   - `item/commandExecution/requestApproval`: the command (or network host) is judged, in the folder Codex says it runs it in (`cwd`); `accept` or `decline`.

   - `item/tool/requestUserInput`: each question goes to Needs me (the recommended option in Run unattended).
   - `mcpServer/elicitation/request`: Ensemble's own server never asks; another MCP server's form with fields is the person's question (§1 step 4), and one without fields (approving one of its tools) is judged as that server's tool.
   - Sign-in token refreshes, attestation and unknown requests are never handled.
3. `item/*` notifications feed the live log and tool count, `thread/tokenUsage/updated` the tokens; the final agent message is the summary. Notifications are handled concurrently; `turn/completed` ends the turn after every earlier one is handled (at most 10 s more), so the final message and the last tool calls are in. The trace (§1 step 6): each command, file change and MCP call is a step from `item/started` to `item/completed` (output, exit code, time), reasoning items are thinking, earlier agent messages are messages. ## 3. Cursor's agent and GitHub Copilot as the engine

Both are driven through ACP, the Agent Client Protocol (JSON-RPC lines over stdio). Every `session/request_permission` is read as a tool call and judged by the same rules as §1; the answer is **allow-once or reject-once, never allow-always**, which would change the person's own allowlist in that tool. `session/update` feeds the live log, tool count, the reply (the task summary) and the trace: `tool_call` to its last `tool_call_update` is one step; `agent_thought_chunk` is thinking. Stop sends `session/cancel`. A chat message continues the agent's session with `session/load`.

**Cursor's agent.** Ensemble starts the person's own `cursor-agent` (on the trusted PATH): `cursor-agent --sandbox enabled|disabled --workspace <folder> acp` (`workspace/engines/cursor.ts`). It uses the existing login (`authenticate` with `cursor_login`); without one it stops with "Run `agent login` there". A run: `initialize`, `authenticate`, `session/new` in the work folder with the `ask_person` MCP server, then `session/prompt` with the task. Cursor's own sandbox is on when the run's is. `cursorCall` reads a command as an `execute` call titled with the command, an edit by its path, and an MCP tool by its `server: tool` title (Ensemble's own tools pass; its browser and capture tools follow the mode). `cursor/ask_question` and form questions (`elicitation/create`) go to Needs me (recommended option in Run unattended; a typed answer goes back verbatim). Tests: `engines/cursor.test.ts`, `engines/cursor.e2e.test.ts`.

**GitHub Copilot.** Ensemble starts the person's own `copilot` (on the trusted PATH) with the sign-in it already has (`workspace/engines/copilot.ts`, `subscriptions/copilot.ts`): `copilot --acp --no-auto-update --no-ask-user --additional-mcp-config @<file> --allow-tool 'ensemble(ask_person)' … --disallow-temp-dir [--sandbox] [--context long_context]`. Copilot's ACP accepts only http MCP servers from the client, so the run's `ask_person` server (and Chat's board tools) comes in through a per-run config file (mode 0600, removed at the end, `timeout` one day so `ask_person` waits for the person); `--allow-tool 'ensemble(<tool>)'` lets Ensemble's own tools run without asking (`ENSEMBLE_OWN_TOOLS` in `engines/judge.ts`: `ask_person`, `report_result`, `attach_evidence`, `ensemble_context`, `secret_http` and Chat's board tools), while its browser and capture tools are asked about and judged by the run's mode like any MCP tool, and `--no-ask-user` sends every question through `ask_person` to Needs me. A session that starts with the person's own `/allow-all` on, or in autopilot or plan mode, is set back to `allow_all: off` and the agent mode before the task goes (`askingCopilot`): left on, Copilot would ask nothing and the judge would see no call. One that cannot be set back is not run.

- **Model, thinking and context.** The task's model, thinking level and context window are given as Copilot starts (`--model`, `--reasoning-effort`, and `--context long_context` for the long window: `contextTier` on the assignment, kept on the job's context and sent to a paired computer as `contextTier`). Switching the model over ACP afterwards puts the session on that model's standard window, so `session/set_config_option` (`model`, `reasoning_effort`) is used only when Copilot did not start on them, and the run then notes that the window may be the standard one. A model the plan does not offer stops the run with that sentence; a level the model does not take is skipped with a note. A run whose reported window is smaller than the long window chosen gets a note saying so. Copilot's `usage_update` (tokens in use, window size) is recorded on the run as `engine_context`; tokens come from each `session/prompt` result.
- **Permissions.** `copilotCalls` reads an `execute` request by its `command`, an `edit` by `rawInput.fileName` and every `locations` path (a patch over several files is judged for each), `read` and `search` by path, `fetch` by URL, and anything else as an MCP tool named by the `<server>-<tool>` title of its `tool_call` update. Reads inside the work folder do not ask; reads outside it, edits, commands, fetches and MCP tools do.
- **Refusals.** Copilot ends its turn when a call is refused. The reasons go back as the next message ("Ensemble refused these tool calls … Continue the task another way within the rules, or finish and say what is left"), at most `REFUSAL_FOLLOW_UPS` (6) times; Copilot's "Operation cancelled by user" note is left out of the reply.
- **Attachments.** The task's originals are copied as for the other engines ([32](32_FILES.md)) and also sent with the first message: images inline (up to 3 MB, when the model takes images), other files as `resource_link`s.
- **Sandbox.** With the run's sandbox on, Copilot's own command sandbox (`--sandbox`: Seatbelt on macOS; bubblewrap with a private network on Linux, which needs `bwrap`, `slirp4netns`, `unshare`, `nsenter`, `iptables` and `/dev/net/tun`) confines its shell commands. Where it cannot run, the run stops with what is missing; with the sandbox off, Ensemble still judges every call Copilot asks about.
- **Sign-in.** Without one, the run stops with "Run `copilot login` there (or press Sign in under Settings → Models)". Copilot answers "Authentication required" both when signed out and when the system keychain holding its sign-in cannot be read (locked, or not ready right after a restart). When its `config.json` lists a signed-in account (`copilotSavedSignIn`, account names only), the run treats it as the keychain and tries again (§3.1); the computer's agent check reports the sign-in as unknown rather than signed out.

A paired computer advertises the engines its runtime has (`capabilities.engines`; runtimes without the list have Claude Code, Codex and Cursor's agent). Assigning GitHub Copilot to a computer whose Ensemble is older is refused with "update it on that computer".

### 3.1 Keeping a run going

Every engine runs under a watch (`workspace/engine-watch.ts`, used by `executeJob` in `workspace/agent.ts`):

- **Stuck.** Quiet for 10 minutes (no output from the engine's process, no tool call running, no question open on Needs me) counts as stuck; one tool call may run quietly for 60 minutes. The engine is stopped and its session carried on.
- **Failures that pass.** The network or the provider's servers, the engine's process dying, or a locked keychain after a restart: the run waits 15 s, 1 min, then 2 min and carries the same session on (`session/load`, `--resume`, the Codex thread) with a message saying why it stopped and to check the files before going on. After 3 tries it ends with the engine's own error. Signed out, not installed, an unknown model and limits are not retried.
- **Minutes.** The run's minutes limit (time on Needs me excluded) ends it as a limit, work kept.

Each carry-on is an `engine_retry` event on the run; its open tool calls end as skipped and the trace goes on.

## 5. Prompts from the tools, and answering in either place

The same hook, installed into each tool's settings, sends prompts to Needs me: Settings → Editors & agents → **Connect** (desktop app or the CLI's runtime), `ensemble hooks connect <tool>`, or `node scripts/ensemble-hook.mjs install --target cursor|claude|codex|copilot-cli|vscode --token …`. Connect signs the hook in with a **`hooks` key**: it can open a card, wait on it, withdraw it and report session activity, never answer a card (`hooksTokenRejected` in `bridge/auth.ts`).

**Which sessions.** Only tasks Ensemble opened in the tool (§4) reach Needs me, identified by the prompt marker or an already linked session; folder proximity is not enough. Any other session gets `skipped` at once. `orchestration.editorRequests` is always `ensemble` (a saved `all` reads as `ensemble`). In a run Ensemble started (§1–§3), the engine channel answers and the person's own hook steps aside (`ENSEMBLE_RUN`).

| Tool | Asks | Reports | Answer in either place |
|---|---|---|---|
| Claude Code and the Claude app | `PermissionRequest`, including `AskUserQuestion` (answered with the questions' `answers`) | `PostToolUse`, `PostToolUseFailure`, `UserPromptSubmit`, `Stop` (in the background) | **Yes.** Claude's dialog stays open beside the card; the first answer counts. Answered in Claude, the card closes ("Answered in Claude Code") when the tool runs, the turn ends or the next prompt is sent |
| Codex (CLI and ChatGPT app) | `PermissionRequest` | `PostToolUse`, `UserPromptSubmit`, `Stop` | Ensemble first; if nobody answers in time, Codex asks itself (its prompt cannot race the hook). Approve the hooks once in Codex (Settings → Hooks, or `/hooks`) |
| GitHub Copilot CLI | `preToolUse` | `postToolUse`, `userPromptSubmitted`, `sessionEnd` | Ensemble first, then Copilot |
| Cursor | `beforeShellExecution`, `beforeMCPExecution` | `afterShellExecution`, `afterMCPExecution`, `beforeSubmitPrompt`, `stop` | Ensemble first, then Cursor |
| VS Code (Copilot agent) | `PreToolUse` | `PostToolUse`, `UserPromptSubmit`, `Stop` | Ensemble first, then VS Code |

Reporting hooks wait at most 5 s and never block the tool. `POST /api/decisions/activity` links the session, closes cards answered in the tool (status `settled`; the waiting hook lets go) and records a hand-off's progress. An answer applies once, for the session, or always. If Ensemble is unreachable or nobody answers in time, the tool shows its own prompt; the hook never allows by itself. `ensemble needs` lists these too.

**Answers in a run Ensemble started** (§1–§3). *Allow for this run* (`scope: "session"`) is kept as a rule of that run (`RUN_RULE_SOURCE`) and read before the person is asked again (`runRule` in `workspace/tools.ts`). It covers the same command with other arguments (`commandKind` in `workspace/command-kind.ts`: the program and its script or what it does, as `python3 <script>`, `npm run build`, `git commit`, `npx playwright test`; never inline code, a variable, `VAR=value` in front, another computer, or a command with an option before what it does, which match only themselves), an edit anywhere in the run's own folder, a fetch from the same site, and the run's other browser tools (or capture tools). *Deny for this run* covers the same. A run on a paired computer takes it from the web and the Node chat too: the computer reports `capabilities.runAnswers: 1`, the web takes *for this run* on a permission (never a question or a push) only for such a computer ("Update Ensemble on <computer> to allow this for the whole run from here. Allow once works now." otherwise), and the computer keeps the rule for its run (`judgeAnswer` in `remote/policy.ts`). The agents' own "always" is never chosen: Ensemble's run rule answers the agent's next ask at once (Claude Code's hook sees every call, so a Claude `updatedPermissions` session rule would add nothing), while an agent's "always" changes the person's own allowlist (Copilot keeps it per folder in `~/.copilot/permissions-config.json`, Cursor in its allowlist, Grok and OpenCode for the project) and hides later calls from the judge.

## 6. Vendor and account boundaries

Engine adapters and subscription turns launch the person's installed, unmodified program with its own sign-in and never copy a vendor token into a hosted model API. Variables that would bill an API account instead of the plan are removed from the program's environment: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` for Claude Code, `OPENAI_API_KEY`, `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN` for Codex, `CURSOR_API_KEY` for Cursor (`KEY_VARIABLES` in each engine). The ACP agents (§3.3), subscription turns (§8) and detection drop all of them plus `XAI_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_GENAI_USE_VERTEXAI`, `OPENROUTER_API_KEY`, `MISTRAL_API_KEY`, `ENSEMBLE_DESKTOP_TOKEN` and `ENSEMBLE_INTERNAL_TOKEN` (`agentEnv` in `subscriptions/detect.ts`). GitHub Copilot, as an engine, in a subscription turn and in detection, also loses `COPILOT_GITHUB_TOKEN`, `GH_TOKEN` and `GITHUB_TOKEN` (which would replace its stored sign-in and reach its shell commands) and `COPILOT_ALLOW_ALL` and `COPILOT_ASSISTED_APPROVAL` (which would approve tool calls without asking), and runs with `COPILOT_AUTO_UPDATE=false` (`copilotEnv` in `subscriptions/copilot.ts`). A tool the person set up with its own model provider (their Codex `config.toml`, Claude Code settings, Copilot's `COPILOT_PROVIDER_*`) runs as set up: the variable a Codex provider reads its key from (`env_key`) is kept even when it is one of the variables above (`codexEnv` in `subscriptions/detect.ts`). Detecting a binary does not prove a plan or model entitlement; the tool reports its own account and quota errors. Vendor terms are the operator's to review.

## 7. Limits

- GitHub Copilot loads the person's own Copilot setup as it would in a terminal: their plugins, skills, MCP servers and custom instructions (`AGENTS.md` and the like in the folder). With many plugins or MCP tools, each message carries a large fixed context. A tool the person already allowed "always" in Copilot for that folder (`~/.copilot/permissions-config.json`) runs without asking, so the judge does not see it; the same holds for a command in Cursor's own allowlist and a tool in Gemini CLI's `tools.allowed`. Copilot's `/allow-all` and autopilot are turned off for the run (§3).
- An engine run cannot be watched or continued in the agent's own app, and hand-offs (§4) cannot be started on a paired computer from the web. Grok Build, OpenCode, Gemini CLI, Antigravity, Mistral Vibe, Qwen Code and Kimi Code have no hand-off.
- Grok Build, OpenCode and Gemini CLI load the person's own setup (their MCP servers, Gemini's and OpenCode's global settings and instructions). `ask_person` waits as long as the agent's own MCP request timeout allows; when the agent gives up, the card is withdrawn (§1 step 4).
- The VS Code and Cursor editors' own folder-trust prompts do not reach Needs me. VS Code's Copilot sign-in is reachable only through the hand-off (§4); code runs and subscription turns use Copilot CLI's sign-in.

## 8. Your AI subscriptions for the assistant

The assistant (the dock, `@ensemble` on a page, the Ask panel) and Ensemble's quick model calls (triage, summaries, a tier's Test) can run on the person's own Claude, ChatGPT, Cursor, GitHub Copilot, Grok, OpenCode, Gemini or Antigravity plan instead of an API key. The plan's agent does the thinking on the person's computer with the vendor's sign-in; Ensemble's tools and data stay where they are. Nothing is billed through Ensemble, and Ensemble never sees the sign-in.

**Signing in.** *Sign in* (web or desktop app) opens a terminal window on that computer running the tool's own login (`claude auth login --claudeai`, `codex login`, `cursor-agent login`, `copilot login`, `grok login`, `opencode auth login`, `vibe-acp --setup`, `kimi login`, or `gemini` or `qwen`, whose first start asks how to sign in; `subscriptions/signin.ts`). The tool opens the vendor's sign-in page and stores the sign-in where it always does. Ensemble checks the tool every 8 seconds for up to 6 minutes.

**One turn** (`subscriptions/agents.ts`). The turn is built as for a model key ([11](11_HOW_THE_ASSISTANT_WORKS.md)): the instructions plus a few lines on how it runs there (`howYouRun` in `subscriptions/turn.ts`: Ensemble's tools, all its own tools in a chat, Ask Ensemble or a routine (below), else its own web search and page reading when `ownWeb` is on (only for Claude Code, Codex and Copilot, `OWN_WEB_AGENTS`: Cursor's agent and the ACP agents get every tool of their own refused in a turn, so they read the web through `hub_web_search` and `hub_read_web_page`), and for a node's turn that the computer's browser and terminal are reached through Ensemble's tools, that real coding goes to a coding-agent session and that the conversation goes on from one message to the next), the message with its context, and the turn's tools (core and playbook tools plus `hub_use_tool`, which calls any of the turn's tools by name).

**One chat, one session** (`subscriptions/turn-sessions.ts`). A chat (its conversation id, the spec's `session.key`) is one session of the agent on the computer that runs it; a new chat is a new session. The computer keeps `<state>/assistant-sessions.json` (chat → agent, session id, the instructions the session was given, its folder and how many days it is kept) and a folder per chat, `<state>/assistant/<key>`, for the turn's files, instructions and MCP config. A turn resumes the chat's session when the agent is the same and the chat is where that session left it (`session.position`, the chat's messages before this one that a session took part in, matches what the session's last turn left; a turn on another model or computer moves it on); it sends only the message. A message that got no answer (its computer was offline, the turn failed before replying) and a failed exchange (the message and its error) do not count (`sessionPosition` in `assistant/agent.ts`), so a routine whose run failed while its computer slept goes on in the same session. For an agent that keeps the instructions from a session's first message (Copilot, Cursor's agent, the ACP agents), changed instructions no longer start a new session: a node's instructions change on most messages (the skills matched to the message, a new memory, the room), and before 0.7.6 nearly every node message left a new session in the person's agent. The message is led by what changed instead (`instructionsUpdate`: "Your instructions changed since this conversation began", the lines now part of them and the lines no longer part of them). When more than half of the lines changed, or after 80 messages in one session (`ROTATE_MESSAGES`), it starts a new session with the chat so far. A session replaced in the store (a new one for the same chat) is deleted from the agent at once, with its folder when the folder is the chat's own.

**A session used outside Ensemble** (`subscriptions/session-touch.ts`). The person can open an Ensemble chat's session in the agent's own app or terminal. After each turn the computer notes how many prompts the agent's own transcript of the session holds (`prompts` in the store: Claude Code's `~/.claude/projects/<folder>/<id>.jsonl` user prompts, Copilot's `user.message` events in `session-state/<id>/events.jsonl`). When the count is higher before the next turn, someone sent it prompts of their own: the chat goes on in a new session with Ensemble's own history, so nothing said there enters the chat, and the touched session is kept unresumed (`retired`) and deleted with the chat or when its entry expires. Other agents, and a transcript the computer cannot read, resume as before.

**Ask Ensemble: one short session per page** (`assistant/ask-sessions.ts`). An inline ask (`@ensemble` in a page, task, project, deliverable or meeting notes; `POST /api/pages/:kind/:id/ensemble`) runs on the tier in Settings → Assistant → *Ask Ensemble model* (`assistant.askTier`, Medium unless changed; the chat's default tier is separate). When that tier is an AI plan, each page has one session per person who asks there (`session.key` `ask-<kind>-<hash of person, kind and id>`, sent without `position`, so the computer resumes it however many asks came before): asking again continues it. Asks on one page by one person are answered one after another in the order they were made (`askInLine`, taken when the request arrives; the waiting ask shows "Waiting for the answer before this one…"), never two at once and never one ahead of an earlier one. When the page's session is gone (deleted in the agent's app), the new one is given the page's earlier asks and answers of that session (`askHistory`, at most 8). Thirty minutes after the last answer (fixed, not a setting) the session is deleted from the person's computers the way a deleted chat's is (below): the account's pending ask sessions are kept in the preference `assistant.ask-sessions` and the scheduler's minute tick sweeps them, so a restart does not lose one; an ask that never reported back is cleared two hours after it began. The session is sent with `keepDays: 1`, so a computer that cannot delete on request yet drops it itself a day later. An ask on a surface (`POST /api/ensemble/invoke`: Today, a board, Needs me, Code; on the chat's default tier) follows the same rules, with one session per surface and the records it is about (`anchorKey`).

**Deleting a chat deletes its session** (`assistant/delete-chat.ts`, `remote/assistant-session-delete.ts`). `DELETE /api/assistant/conversations/:id` stops a reply still running, deletes the chat and its messages, then asks each of the person's computers that runs assistant turns to drop that chat's session: `dropSession` removes the store entry, deletes the session in the agent itself (`deleteNativeSession`, the same delete as above, for every subscription agent) and the chat's own folder, after any turn of that chat still running there has ended. A computer that is away, or does not confirm, is asked again when its event stream next opens, and while it is online every 5 minutes from the scheduler's minute tick (`retryAssistantSessionDeletes`); pending requests are kept per computer in the `assistant.session-deletes` preference for 30 days (the time after which a computer drops an unused session itself), and those of a computer no longer paired are dropped. On the desktop app or CLI runtime the session is dropped directly. Deleting a routine deletes its conversation the same way (`dropRoutineChat` in `routines/service.ts`), from the Routines page or the assistant; a routine's turns keep their session unused for twice the gap to the routine's next run, 30 to 90 days (`routineKeepDays`), so a weekly or monthly routine stays in one session.

**A group of chats, one project folder.** A turn may name a group (`session.group {id, name}`, with `session.keepDays`): its agent then works in the group's project folder (`projectFolder` in `workspace/agent-projects.ts`, `<workspace>/projects/<name>`), so the agent's own app lists the group's sessions together, as it groups sessions by folder; the turn's own files stay in the chat's folder. An Ensemble Node's turns use the node as the group ("<Name> (Ensemble Node)") and keep a session 7 days unused (§10.2). Turns of one chat run one at a time; otherwise it starts one, with the chat so far (`session.history`, the last 12 messages) before the message. A session the agent cannot reopen, or an agent too old to keep one, falls back to a new session or none, with the chat so far. Sessions unused for 30 days (or the chat's `keepDays`) are dropped and deleted from the agent. A computer before `assistantTurns: 3` (`ASSISTANT_TURN_SESSIONS`) gets the chat so far in front of every message; a one-off completion (`complete` on a subscription: triage, a summary, a title) keeps no session, and leaves none in the agent: Claude Code runs it with `--no-session-persistence` and Codex in an ephemeral thread, while the session Copilot (named with `--session-id` from 1.0.78), Cursor's agent and the ACP agents save is deleted once the turn is over (`dropOneOff`), in the folder the turn ran in (Gemini CLI, OpenCode and Grok Build find a session by the folder it began in), which is removed after.

**The agent's own tools in a chat** (`subscriptions/own-tools.ts`, `assistantTurns: 4`). A chat, an Ask Ensemble or a routine (`ownTools` on the turn's spec; never a node's turn, which reaches the computer through Ensemble's tools so its owner approves, nor a one-off completion, whose input is a file, an email or a meeting the person did not write) keeps all of the agent's own tools: its shell, files, web search and its own built-in tools, as in the person's own agent, without asking. Ensemble decides nothing about what the request needs: the instructions (`howYouRun` with `ownTools`) say most requests need only Ensemble's tools, that a command or a file on the computer is the agent's to judge, that its folder is the chat's scratch folder (keep work in Ensemble with `hub_save_file` or a page, or where the person says), and that a change to code in a repository usually goes better as a task for a coding agent (`hub_assign_to_agent`) unless the person asks for it here. Only the hard floor refuses a call, judged from the turn's folder (`judgeFloor` in `workspace/engines/judge.ts`, the same floor a run has: the dangerous commands, privilege, persistence and system-settings programs, and outside that folder keys and sign-ins, Ensemble's own data and code, start-up items, the system's files and other accounts); a refused call comes back to the agent with its reason and the turn goes on. Each agent is asked its own way: Claude Code runs every tool through a PreToolUse hook (`--settings`, `scripts/ensemble-hook.mjs --chat`, which asks the turn's runtime at `POST /api/engine/assistant/ask` with the turn's secret and fails closed); Copilot CLI gets every tool, path and URL (`--allow-all-tools --allow-all-paths --allow-all-urls`, its built-in MCP servers on) and the same hook as a per-turn plugin (`--plugin-dir`, a `plugin.json` and `hooks.json` in the chat's folder: a folder's own `.github/hooks` load only for a new trusted session, a plugin for a resumed one too), from a Copilot whose help lists `--plugin-dir`; Codex runs without its sandbox and with its environment (no `environments: []`), asking before every command it does not consider safe and every file change, each answered by the floor (`answerCodexOwnTools`); Cursor's agent runs with `--sandbox disabled` and Cursor's and the ACP agents' permission requests are answered by the floor (`answerAcpOwnTools`). Each of its own calls, with its input and what it returned, and each refusal with why, goes in the person's AI activity log (`OwnToolLog`, [07 §1.4](07_MODULE_GOVERNANCE_AUDIT_METRICS.md#14-the-ai-activity-log)). A computer before `assistantTurns: 4` (`ASSISTANT_TURN_OWN_TOOLS`) runs the turn with Ensemble's tools only, and its agent is told so (`systemWithoutOwnTools`). Otherwise the agent gets only Ensemble's tools:

- **Claude Code:** `claude -p [--input-format stream-json] --output-format stream-json --verbose --include-partial-messages --system-prompt-file <file> --tools "" --strict-mcp-config --mcp-config <file> --allowedTools mcp__ensemble --permission-mode default (with own web: --tools "WebSearch,WebFetch" --allowedTools mcp__ensemble,WebSearch,WebFetch) --setting-sources user (--session-id <id> | --resume <id> | --no-session-persistence) --max-turns 28 [--model] [--effort]`, message on stdin (with files, one stream-json user message), in the chat's folder. The instructions go with every turn (Claude Code does not keep them in a session). Model, level and the tier's long window go through `claudeLaunch` as for a run (§1). No shell or files of its own; web only with own web. The person's user settings load (where Claude Code may keep how it signs in), never a folder's; their MCP servers do not; Ensemble's hook steps aside (`ENSEMBLE_RUN`); the turn is not saved as a Claude Code session.
- **Codex:** `codex app-server`, a thread with Ensemble's instructions as `baseInstructions` (`thread/start`, kept for the chat; `thread/resume` on its next turn, with the instructions again; ephemeral for a one-off), every `turn/start` with `environments: []` (a resumed thread does not keep it), a read-only sandbox without network (with own web, Codex's own `web_search: "live"`), `environments: []` (no shell or file tools; a Codex that rejects the field starts without it), every approval declined (`answerCodexTurn`).
- **Grok Build, OpenCode, Gemini CLI, Antigravity, Mistral Vibe, Qwen Code, Kimi Code:** started as for a run (§3.3) in the chat's folder, with Ensemble's instructions leading a session's first message (`session/new`; `session/load`, or Antigravity's `session/resume`, after, when the agent offers it); a session that starts in a mode that acts without asking is set to the asking one first (Antigravity, Vibe), so nothing of the agent's own runs unasked; the tier's model and thinking level from the session's options; every permission refused except Ensemble's tools (`answerAcpTurn`).
- **Cursor's agent:** ACP with Ensemble's instructions leading a session's first message (`session/load` after); every permission refused except Ensemble's tools (`answerCursorTurn`); the turn's tokens from `session/prompt`'s `usage`.
- **Copilot CLI:** `copilot [-p <prompt>] --stream on --output-format json --allow-all-tools --deny-tool shell --deny-tool write [--deny-tool url --excluded-tools web_search, without own web] --disable-builtin-mcps --no-ask-user --no-auto-update --additional-mcp-config @<file> [--session-id <id>] [--attachment <file>…] [--model] [--reasoning-effort] [--context long_context]`; the long window when a tier set to that Copilot model chose it (`context` on the tier, `tierContext` in `subscriptions/turn.ts`, sent to a paired computer on the turn's spec). From Copilot 1.0.78 (`copilot --version`, asked once per process) the prompt is piped on stdin, which no command line limits; before, it goes as `-p` and is cut to 28,000 characters on Windows (200,000 elsewhere), oldest text first, which could cut a node's instructions. `subscriptions/copilot-output.ts` reads `assistant.message_delta` and `assistant.message` from that process, and the turn's tokens from `--usage-output-file` (Copilot 1.0.81 on; `modelMetrics[model].usage`, input counting cache reads and writes), which holds the whole session's totals: the computer keeps them with the chat's session (`usage` in `assistant-sessions.json`) and a resumed turn counts only what it added; per-call `assistant.usage` events, from a Copilot that sends them, are the turn's own; missing counts stay null, and Copilot's billing units (`cost`, `totalNanoAiu`) are never treated as USD or credits. No quota endpoint or session history is read.

The agent's environment is cleaned as in §6.

**Files on the message** (`subscriptions/turn-files.ts`). Every file attached to the person's message is delivered to the agent's computer: it travels with the turn as `files` (`TurnFile`: id, name, media type, kind, size; `TURN_FILES_MAX` 8), passed to `runSubscriptionTurn` with a reader. The desktop runtime and a computer that reports `assistantTurns: 2` get the files; an older computer gets a note after the message naming them and saying Ensemble on that computer must be updated to receive files ([25 §4.9](25_REMOTE_TASKS_ON_YOUR_COMPUTER.md#49-subscriptions-and-included-models)). `runAgentTurn` downloads each file into the turn folder's `files/` (`saveTurnFiles`, names made safe with `diskName`, a repeat gets " (2)"), skipping a file over 32 MB and anything past 64 MB together. Each file then goes inside the agent's message in the agent's own input form. A file stays out of the message only where putting it in would fail the whole turn, because the agent's message format has no place for that kind; the message names it, says it is saved in `files/` and why it is not inside the message. Ensemble does not read files for the agent and its extracted text is not added (`files/extracted-text-policy.ts`, off). A text file's own contents are the file and go as they are.

**Tools.** The agent starts Ensemble's MCP server (`scripts/ensemble-ask-mcp.mjs` with `ENSEMBLE_ASSISTANT_TURN`), which lists and calls the turn's tools through this computer's loopback API (`GET /api/engine/assistant/tools`, `POST /api/engine/assistant/tool`) with the turn's own secret (`subscriptions/bridge.ts`). Each call runs where the data is, through the same code as a model-key turn (`runOne` in `assistant/agent.ts`): same space, write policy and refusals, at most 24 calls per turn (`MAX_COMPUTER_CALLS`; an Ensemble Node's turn 60, as `maxTurns` is capped at 64 for older computers). A turn on the person's plan spends none of Ensemble's included credits: `hub_web_search` skips Foundry's search there (`ownPlan` on the tool context) and answers from the free search, and a node's `web_task`, which runs on a server model, is left out. Every agent waits up to 10 minutes for one call (`TOOL_TIMEOUT_MS`: Claude Code's `MCP_TOOL_TIMEOUT`, Codex's `tool_timeout_sec`, the `timeout` in Copilot's MCP config, whose own default is shorter), as a node's browser task or a slow connected app takes minutes; a relayed turn whose computer is waiting on a call is working, not quiet (`quiet` in `subscriptions/relay.ts`), so only the 20-minute limit ends it. When `hub_how_to` loads a playbook, its tools are added and the server sends `notifications/tools/list_changed`. In the desktop app the tools run in its own process; from Ensemble on the web the turn travels to the computer and back ([25](25_REMOTE_TASKS_ON_YOUR_COMPUTER.md)).

**Problems are said in words:** no computer paired, none online (with when last seen), Ensemble too old there, the agent missing (with the vendor's install link), not signed in (with where to press Sign in), the plan's limit reached (shown like a quota), or the agent's own message.

Tests: `subscriptions/subscriptions.test.ts` (including each agent's form for files), `subscriptions.integration.test.ts` (the file route), `agents.e2e.test.ts`, `remote/assistant.test.ts`.

## 9. The worker's report and evidence

A coding agent reports its own result, separate from its closing words, and attaches what its owner should see (`evidence/run-tools.ts`). Ensemble Node reads the report to decide whether a step is done ([35 §8.12](35_ENSEMBLE_NODE.md#812-results-and-evidence)).

**The tools.** A task run's `ensemble` MCP server (`scripts/ensemble-ask-mcp.mjs`) has `report_result`, `attach_evidence`, `ensemble_context`, `ensemble_search`, `ensemble_actions`, `ensemble_act` and `secret_http` next to `ask_person`, and the browser and capture tools of the computer (below); a Chat run has the board tools and `ensemble_context` instead. Its `initialize` answer carries `instructions` (`instructionsFor`): the agent acts in Ensemble through this server and its brief, and never opens Ensemble's web app to sign in or to read the person's work ([39 §4](39_ENSEMBLE_TOOLS_AUDIT.md#4-never-ensemble-in-a-browser)). Every engine loads that server, so every engine has them. They reach `POST /api/engine/tool` on loopback with the run's secret, and the judge passes them without a prompt (`ENSEMBLE_OWN_TOOLS` in `engines/judge.ts`; Copilot's `--allow-tool 'ensemble(<tool>)'`).

| Tool | Input | What happens |
| --- | --- | --- |
| `report_result` | A `StepReport` (`node/report.ts`): `outcome` (`done`, `pass`, `fail` or `blocked`), `summary`, and optionally `checks` (each with its verdict), `subject` (the commit or content hash it produced), `evidence` and `blockedBy` | Checked: its shape, and that the candidate exists (`subject.commit` is in the folder's repository; `subject.contentHash` is the last commit's tree or the working tree's, worked out with a throwaway index). Then redacted and kept on the job (`workspace_jobs.report`, a `report` event). A refusal is the tool's answer, so the agent can fix it and call again. A later call replaces the report. |
| `attach_evidence` | `{path, kind, caption?, requirementId?}`; `kind` is `screenshot`, `image`, `video`, `trace`, `report`, `log` or `file` | A file outside the run's folder is judged as a read by the run's rules first. The file is checked and copied into the run's evidence folder (below), with an `evidence` event. The answer gives its id, for `checks[].evidence`. |
| `ensemble_context` | `{item?, rel?, offset?, limit?}` | The person's records around the task (`workspace/context-tools.ts`, [03 §5](03_MODULE_CONTEXT_ENGINE.md#5-shared-retrieval-and-briefs)): without `item` the task's context packet (its meeting and the words asked, project, people and roles, dependencies, related open work, done-before, files); with an `ensemble://<kind>/<id>` handle from a result, that record and its links; with `rel`, one relation in pages. A task claimed from Ensemble on the web is answered there, for the job's space, under the job's lease (`POST /api/devices/self/jobs/:id/context`); otherwise this computer's Ensemble answers. |
| `ensemble_search` | `{query, kinds?, limit?}` | Task runs only (Chat keeps its board search). Ranked word search across the person's records, closest to the task first, each hit with a handle for `ensemble_context`. Answered where `ensemble_context` is. |
| `ensemble_actions`, `ensemble_act` | `{groups?, names?}`; `{action, input}` | Task runs only. Ensemble's everyday changes around the task, the part of an editor's key's allowlist not marked `keyOnly` ([CONTEXT_BRIDGE §5.1](CONTEXT_BRIDGE.md#51-changes-in-ensemble)), without the connected apps: update the task's fields, add or edit pages, put a task or page on a board, make a diagram or plot, link people and projects, add a meeting note (`runRunAction` in `workspace/context-tools.ts`). A task claimed from Ensemble on the web is answered there under the job's lease (`POST /api/devices/self/jobs/:id/act`), and only in the computer owner's own space; a local task on this computer's Ensemble. Changes run at once and are in Ensemble's Undo |
| `secret_http` | `{ref, url, method?, headers?, body?}` | Also in Chat runs. A request this computer makes with a saved secret put in where `{{NAME}}` appears in a header or the body, only to that secret's allowed origins and only when the run may use it; the answer has the value hidden ([35 §8.7](35_ENSEMBLE_NODE.md#87-secrets), `credentials/secret-http.ts`). A run whose internet is off is refused. |

**Secrets by reference.** A run that may use a secret with allowed destinations is told its name and where it may go, never its value (`secretRules` in `lib/run-secrets.ts`), and, when the run names the secret, gets git settings that make git over https to those hosts sign in with it (`credentials/git-credential.ts`). The secret is never in the run's environment.

**Browser and capture.** The server also lists `browser_*` and `capture_*` ([25 §10](25_REMOTE_TASKS_ON_YOUR_COMPUTER.md#10-browser-and-capture-on-the-computer)), as `GET /api/engine/tools` gives them for a task run: all of them when the computer has a browser for Ensemble, else only `capture_status`, which says what `ensemble capture setup` adds. A call runs for the run's own operation (its job), writing into its evidence folder (`evidence/capture-tools.ts`). They follow the run's mode like any MCP tool, for every engine: Review only and Run unattended use them freely, Ask asks before them (*Allow for this run* on one browser tool covers the run's other browser tools, and the same for capture), a read-only run is refused. What it writes is the run's evidence at once, with no `attach_evidence`: the answer names each file's id (to put in `checks[].evidence` after `capture_check`), or says it is held for the owner's preview (a saved secret or key on screen, a desktop app's window, a site the owner previews first); a held file goes nowhere until the owner releases it ([35 §8.16](35_ENSEMBLE_NODE.md#816-browsing-and-capture)). A run with the internet off opens and loads only this computer's own addresses (`loopbackOnly`). `capture_app_start` starts an app in the run's folder (or one it was let into), sandboxed as the run is. A run may read its own evidence folder, to look at its screenshots. When the run ends, a recording still going is finished and kept, and its tabs, apps and displays end (`finishRunCapture`).

**Instructions.** Every engine's brief has one line on this (`reportingNote` in `workspace/agent.ts`, part of `workingNotes`): at the end call `report_result`, after `attach_evidence` for files the owner should see (with the path of the run's evidence folder), and without MCP tools write the report as JSON to `.ensemble/result.json`. A `commit` or `contentHash` at the top of a report is taken as its `subject`.

**Without MCP.** When the run ends with no report from the tool, the runtime reads `.ensemble/result.json` in the run's folder (`collectRunResult`). It reads only a regular file with one name, at most 256 KB, written during this run, without following links. It must be a valid `StepReport` with a candidate that exists. The files it names under `evidence` (kinds `screenshot`, `video`, `report`, `log`, `file` or `evidence`; not URLs) are attached under the same checks, and so is any file left in the run's evidence folder. A problem is recorded as a `report_refused` or `evidence_refused` event; it never fails the run. Chat runs and interrupted runs are not read.

**The evidence folder** (`evidence/files.ts`) is `<Ensemble's data folder>/evidence/<job id>`, never in the repository. Agents cannot write there (the sandbox denies Ensemble's data folder), so the runtime copies each file in. A file is read once, by descriptor:

- opened without following links (`O_NOFOLLOW`); a regular file with one name only (a hard link is refused); its real path is checked again after opening, so a file swapped after the check is refused;
- never a credential file: `.env*`, key and certificate files (`*.pem`, `*.key`, `id_rsa*`, `id_ed25519*` and the like), credential stores (`.npmrc`, `.netrc`, `.git-credentials`…), shell histories, or anything under `.ssh`, `.aws`, `.gnupg` or `.git` (`credentialPathReason` in `evidence/limits.ts`);
- nothing in Ensemble's data folder or the browser profile folder, and nothing the outside floor refuses to read (`outsideRefusal`: keys, sign-ins and browser data in the home folder; `evidenceFloor`);
- never a file that holds a saved run-secret value;
- at most 100 MB per file, of any kind, and 100 files per run;
- the kind must match the type read from its bytes (a `screenshot` must be an image).

What is copied is exactly what was checked, and the copy is checked again before it is sent. Folders of runs that ended 30 days ago are removed. A paired computer uploads each file to the web unless `ensemble evidence off` ([25 §4.11](25_REMOTE_TASKS_ON_YOUR_COMPUTER.md#411-the-workers-report-and-evidence)).

Tests: `src/evidence/report.integration.test.ts` (the MCP server end to end, content hashes, the result file), `src/evidence/files.test.ts` (the file rules), `src/evidence/capture-run.integration.test.ts` (the browser and capture tools through the MCP server: listed for task runs only, captures kept and held, a blank screenshot failing its check, internet off, a recording finished at the run's end, held files to newer and older servers) and `src/evidence/captures.test.ts` (recording captures as evidence).
