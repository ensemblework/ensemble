# 41 · Agent sessions

Continue an agent session when the next task builds on earlier work. Start a new one when the work needs a separate conversation. A session belongs to the coding agent on the computer that ran it.

Find sessions in **Assign → Continue an earlier task**, Ensemble Node's **Sessions** page, or `ensemble sessions`. The Hub has no standalone session list.

## At a glance

| Session | When it continues | When it is cleaned up |
| --- | --- | --- |
| Coding tasks and terminal chats | You continue an earlier task, or Ensemble selects a fitting session | After all its tasks are retired, or when you delete it |
| Code tab agent thread | Each message in the thread, with the same agent and plan; another agent or plan, or a fork, starts a new session with a handoff record | After the thread leaves the Bin (7 days, or deleted for good there), or when you delete the session |
| Node's own coding session | The node continues its work | After seven days without a run starting or finishing |
| Assistant chat on an AI plan | Each message while the agent and conversation still match | With the chat, when replaced, or after 30 unused days |
| Routine on an AI plan | Each routine run | With the routine, or after twice the gap to its next run, bounded to 30–90 days |
| Ask Ensemble on an AI plan | Each ask on the same page or surface, in order | 30 minutes after the last answer |
| Node conversation on an AI plan | Each message in that conversation | After seven unused days |
| One-off summary, triage or title | Never | When the completion ends |

Settings → Agents → **Agent sessions** has three switches, all on by default: **One folder per project**, **Continue a fitting agent session**, and **Clean up agent sessions**.

## 1. Coding sessions

To continue explicitly:

1. Open **Assign → Continue an earlier task**.
2. Choose the session that contains the relevant work.
3. Review its computer, folder, agent and model settings.
4. Start the next task.

The run uses the session's computer, folder and agent. It keeps the model, thinking, context and fast-mode settings unless you name replacements. Changing one option preserves the others. Another model of the same agent and plan goes on in the session from the next run. A different agent, plan or computer cannot resume that same session.

A run starts its agent conversation in one of four ways:

| Operation | When | What the agent gets |
| --- | --- | --- |
| Fresh | Nothing before it, or its earlier session was deleted in Ensemble | The whole brief |
| Resume | The same agent and plan continue | Only the new work (in the Code tab, only what changed and the message) |
| Handoff | A Code tab thread switches agent or plan, or the agent no longer has its session | A new session, with a handoff record of the earlier one |
| Fork | *Fork from here* on a Code tab turn | A new thread and session, with a handoff record of the thread up to that turn |

A **handoff record** is a summary Ensemble makes from the earlier session's runs, without a model: what you asked, each acceptance criterion with its evidence, what worked and what failed, your decisions, files, checks, artifacts, the next step and blockers. It is marked as information and never as the whole conversation, the part the agent gets is at most about 8,000 characters, and the full record is kept in Ensemble and in `.ensemble/handoff/<id>.md` in the folder, out of git.

If the agent's conversation is missing or expired, Ensemble starts a new session in the same folder with the full brief and the earlier result. The task page explains that the earlier conversation was not remembered. A session deleted through Ensemble is also restarted separately; it is never reopened.

Codex can't continue a conversation while the ChatGPT app has it open. The run waits up to ten minutes, and its card says "Waiting for the ChatGPT app to let go of this conversation." Switch to another chat in the app, or quit the app, and the run goes on in the same conversation. If the app keeps it open the whole time, the run starts a new session as above, and the task page says why. The earlier conversation is kept and deleted with the session.

Continuing a task keeps its existing folder grant, including across a chain of runs.

## 2. One folder per project

Leave **Settings → Agents → Agent sessions → One folder per project** on to group eligible project tasks in one working folder. A task with an explicit folder, repository, earlier session or other assigned workspace keeps that choice.

Project-folder runs take turns so two runs do not change the same folder at once. The folder includes the project's current brief: its summary, notes, page, repositories, people and upcoming deliverables. The agent is told to reread it when it changes.

Renaming a project keeps its folder and sessions. A removed folder is recreated when needed; projects with the same name receive distinct folders. Turning the switch off stops this automatic grouping for new work.

If you start sessions of your own in a project's folder (a Claude Code or Copilot session there, or a new thread in its Codex project), the project's next task is told about them: their title, last message and files changed. They stay yours. Ensemble only reads them, and never continues, renames, moves or deletes them.

## 3. In the agents' own apps

Ensemble attempts to give sessions meaningful titles and group project work in the agent's app. This is best effort and never fails the task.

| Agent app | What to expect |
| --- | --- |
| ChatGPT app with Codex | Supported versions show task titles and Ensemble projects. Project-sidebar changes wait until the app is closed, then appear when you reopen it |
| Claude app, Code tab | Supported profiles receive named session records. Reopen an already-running app to see new records. A session you delete in Ensemble is gone from the list once the app has been reopened |
| GitHub Copilot | Sessions group by working folder; new task and chat sessions receive a title. Copilot in VS Code runs inside VS Code: Ensemble needs Copilot CLI, which **Set up** in Settings → Models installs |
| Cursor | ACP sessions are separate from the app's history and terminal resume history. A new session's first message starts with its title, which Cursor names the session from. The app's Agents window keeps its own copy of the agent, which Ensemble does not use: with only the app, **Set up** in Settings → Models installs Cursor's agent |
| Grok Build, OpenCode, Gemini CLI, Qwen Code, Kimi Code, Mistral Vibe | These agents cannot be given a session title, so a new session's first message starts with its title, which their session lists show or name the session from |
| Antigravity | Ensemble's agent-server sessions are separate from the Antigravity app's history |

Each assistant chat works in a folder named after the chat, so apps that group sessions by folder, such as the Claude app's Code tab, show the chat's name instead of an id. A chat keeps its folder while its agent session lasts, so renaming the chat does not rename the folder.

Your own project names and manual project choices are preserved. Removing a project in the agent's app does not make Ensemble recreate it automatically. Claude's cloud chat Projects are separate from its Code-tab folders.

## 4. Choosing a session

With **Continue a fitting agent session** on, a new task can reuse an idle session of the same agent on that computer. Candidates must belong to the same account, space and project, or both have no project. Sessions do not cross those boundaries.

Ensemble compares linked tasks, deliverables, meetings, page context, named files or issues, topic similarity and available context space. It uses deterministic matching, without a model call. Busy, old, deleted, unavailable or overly full sessions are excluded.

The run card states which session was continued and why. If the relevant session is too full, a fresh one can receive its last report instead. When the match is uncertain, Ensemble starts fresh.

Choose **Assign → More options → Always start a new agent session** to skip matching for one run. Turn off the setting to disable automatic matching generally. Explicit folders, repositories, pull requests, chats, retries and Node plans follow their own choices.

## 5. Assistant chats on an AI plan

An assistant chat normally uses one conversation with the plan's agent. Each later message resumes it while the same agent and conversation position still match. A failed exchange does not by itself break continuity.

Changing model or computer, losing the agent session, or rotating a long session can start a fresh one with Ensemble's recent conversation context. For agents that keep their initial instructions, small instruction changes are sent as updates; major changes or 80 messages trigger a fresh session.

You can open a chat's session in the agent's own app (the Claude app, Codex in the ChatGPT app, Copilot, Cursor and others) and keep talking there. Ensemble doesn't watch the app. The next time you write in the Ensemble chat, it first brings in what you and the agent said there, marked "In the Claude app" (or wherever it was) with the time. Then it goes on in the same session, so the agent remembers both. Tool calls show as one line, such as "Edited 2 files, ran 3 commands". At most the latest 20 exchanges come in, and the chat notes how many earlier ones were left out. If that message fails or you stop it once the agent has it, what you said in the app stays in the agent's session but isn't brought into the chat.

### Ask Ensemble sessions

Repeated asks on the same page use one short session per person. They are answered one at a time in the order received. A missing session restarts with up to eight previous asks and answers. It is deleted 30 minutes after the last answer.

Page asks use **Settings → Assistant → Ask Ensemble model**, normally Medium. Surface asks, such as Today or Board, use the chat's default tier. The two choices are separate.

## 6. Deleting and cleaning up

Delete a coding session from Node's **Sessions** page. A node's deletion request appears as an owner-only confirmation card. Every computer that ran the session must be online and support deletion; otherwise Ensemble tells you which computer to connect or update and leaves the session visible.

Deleting a session cancels its queued runs and removes the agent's saved conversation, found by its exact id: your other conversations in that agent are left alone. Ensemble's run records, project folders and files remain. Continuing one of its old tasks starts a separate session.

Automatic cleanup checks every 15 minutes. A coding session becomes eligible when all its tasks are deleted for at least ten minutes, or are done or dropped beyond the completed-retention window and not pinned. Active or queued work is left alone. Offline computers and failed deletions are retried later.

Deleting an assistant chat stops its reply and requests deletion of its agent session and scratch folder. Offline computers are asked again when they reconnect. Deleting a routine removes its conversation in the same way.

A Claude Code session you delete leaves the Claude app's Code tab when the app is next reopened. While the app stays open it may still list the session, because it keeps its list in memory; Ensemble keeps removing what the app writes back until the app has been closed.

Deleting a project keeps its folder and agent sessions. Its Ensemble-created Codex project is removed after ten minutes in Trash, leaving time for Undo. Restoring the project after that can create a new Codex project for its next task.

## In the code

A session is one saved conversation with the person's own agent (Claude Code, Codex, Cursor's agent, GitHub Copilot, Grok Build, OpenCode, Gemini CLI, Antigravity, Mistral Vibe, Qwen Code or Kimi Code) on their computer. Ensemble starts sessions for task runs and terminal chats ([30](30_ENGINES.md)), for assistant chats, asks and routines on an AI plan ([30 §8](30_ENGINES.md#8-your-ai-subscriptions-for-the-assistant)), and for Ensemble Node ([35 §8](35_ENSEMBLE_NODE.md#8-work-on-a-computer)). This page covers how sessions are continued, chosen, grouped by project, shown in the agents' own apps, deleted and cleaned up.

Paths below are under `apps/hub-api/src/` unless qualified.

### At a glance: implementation reference

| A node's own coding session | Run a node starts for itself | By the node | None of its runs started or finished in 7 days (§6) |

### 1. Coding sessions: implementation reference

A coding session (`workspace/sessions.ts`) is one conversation with a coding agent (Claude Code, Codex, Cursor's agent, GitHub Copilot, Grok Build, OpenCode, Gemini CLI, Antigravity, Mistral Vibe, Qwen Code, Kimi Code), carried across the runs that continue each other (`continueFromJobId`) with the same agent. It is derived from the runs, not stored: its id is its first run's id, its agent session is the newest `engine` event in it, and the chain's resource key keeps it to one turn at a time.

A thread of the Code tab's agent ([16 §9](16_CODE_TAB.md#9-the-agent)) is such a chain of chat runs on one internal task off the board (`sourceRef` `code:<key>`), so the thread is the session: no second store. Its title is the task's: first a short name from the first message, then one the person's Low tier gives it (unless renamed meanwhile); deleting the thread puts it in the Code tab's Bin for 7 days (restorable there), after which the task is deleted for good, and its session goes with retired work (§6).

- Continuing a task in a session (Assign's "Continue an earlier task", the assistant's `session`, `Assign.session`) resumes the agent's own conversation (`earlierSession` walks back to the nearest recorded session) and sends the new task with a line saying it continues there (`sessionTaskPrompt`); the agent keeps what it learned and its prompt cache. A session that cannot be reopened (`SessionGoneError`) runs as a new one with the full prompt.
- **A session that no longer exists.** The person may delete a session in the agent's own app, or the agent may expire it (Claude Code after 30 days). Every agent says so when asked to reopen it (Claude Code: "No conversation found", exit 1; Codex: "no rollout found for thread id"; Copilot, Cursor and the ACP agents: `session/load` refused), and the run goes on in a new session in the same folder with the full brief, which has the earlier task's title, outcome and summary ("This continues an earlier task"). Every agent keeps a session's id when it resumes it, so the web tells a resumed run from a restarted one by the ids computers already send (`sessionRestartOf` in `workspace/session-continuity.ts`): the task page says the earlier session no longer existed, the run's `SessionChoice.outcome.resumed` is false, and a node is told in its run note that the agent did not remember the earlier conversation.
- **A session the agent's own app holds.** The ChatGPT app runs its own Codex app-server. A thread it has loaded (open in the app, or only looked at) has an active writer there (`~/.codex/thread-writer-locks`), so `thread/resume` from Ensemble's app-server answers `-32600 thread <id> already has an active writer`. That thread is not gone (`ACTIVE_WRITER` in `workspace/engines/session-restart.ts`). The Codex engine tries again every 30 seconds for up to 10 minutes (`resumeCodexThread`, `BUSY_WAIT.task`). The wait runs under `ctx.waitForRun`, so it neither uses the run's minutes nor counts as stalled. The run card says "Waiting for the ChatGPT app to let go of this conversation. Switch to another chat in the app, or quit the app." After the limit the engine throws `SessionBusyError`, and the run starts a new session as for a missing one. `sessionRestartOf` then answers `busy`, and the task page and a node's run note say the app held the conversation. The held thread stays on the earlier run's `engine` event, so deleting the session deletes it too.
- **Why a run restarted its session** is recorded: the `engine_new_session` event and the new session's `engine` event carry `restart: { reason: "gone" | "busy", error }`. The `engine` event is relayed to the web with every engine, so `sessionRestartOf` reads it there. The run's `model.call` metric and its AI-activity entry carry the same `restart`, and the computer logs a warning line.
- **A session the person used in the agent's own app** (`workspace/outside-runs.ts`). A run notes how many prompts its session holds as it ends, however it ends: a local `session_prompts` event `{ session, prompts }`. A prompt sent before the run failed, was stopped or was interrupted is in the session all the same, so `executeJob` (`workspace/agent.ts`) notes the count then too, alongside the run's wrap-up, and ends the job only once the note is written: the next run in the session starts after that. Claude Code's and Copilot's transcripts and Codex's `thread/read` give the count. Cursor's and the ACP engines count the prompts themselves: those in the history the agent replayed as the run reopened the session, plus the ones the run sent, where a prompt the agent left unanswered and the next one count once, as the agent replays them (`acpPrompts`). They return the count (`EngineResult.prompts`) or carry it on what they throw (`withPrompts`). A count that cannot be made is noted as `null`. A run that continues the session reads what came after the count, with the same readers as a chat (§5). Claude Code's, Copilot's and Codex's history is read before the agent starts (`runOutside`). Cursor's agent and the ACP agents replay theirs on `session/load`, and the engine hands that history to the run before it sends the prompt (`onReplay`, `replayOutside`), once a run, since by a retry the session also holds the run's own prompts. The run adds a step "From the Claude app" (or wherever) with the exchanges, which the task page shows with the run's steps. Its brief opens with a short note: "Since the last Ensemble run, <name> said in the Claude app: …". It records the import as `agent.outside`, and the session goes on. Nothing is brought in when no run noted the session's prompts yet, when the last count is `null`, or when another run used the session after it and noted nothing (Ensemble quit or the computer lost power as it ran: `promptsNoted`), nor from a replay longer than 50,000 updates (`MAX_REPLAYED`) or an Antigravity session, which `session/resume` reopens without replaying it.
- **A session deleted in Ensemble** (by the person, a node, or the clean-up) is not reopened at all (`sessionToResume`): a run continuing one of its runs ("Continue an earlier task" lists them as "its agent session was deleted: a new one starts there") works in that folder in a session of its own (`continuesSessionOf` in `workspace/sessions.ts`), which is listed, chosen and cleaned up like any other; the deleted session keeps only its own runs.
- A run that continues a run in a folder the person granted (a shared folder) works in that folder however long the chain, since only the first run carries the grant (`grantedFolderOf` in `workspace/agent.ts`).
- `Assign.session` (any run id in it) runs on the session's computer, under its current pairing, in its folder, with its agent, model, thinking level, context window and fast mode unless others are named (a run profile's do not apply); another agent or computer is refused. Each setting is kept, reset to the agent's own default (`"default"`, or `fast: false`), or set as named, separately (`sessionChoices` in `workspace/assign.ts`): naming a model keeps the thinking level and context window. The task's model tier adds nothing to a run in a session.
- `GET /api/agent/sessions?taskId=&deviceId=&q=&limit=` lists the person's sessions, newest first, each with agent, model, computer, folder, first and latest task, a one-line summary of the latest report, status (`working`, `waiting`, `queued`, `idle`) and whether it can be resumed; `GET /api/agent/sessions/:id` reads one, and a job's detail carries its `session`. The web shows no session list.
- **Session operations** (`sessionOperation` in `workspace/sessions.ts`): `fresh` (no run before it, or a deleted session), `resume` (`continuesSessionOf`: the same agent and subscription, not a fork, the session not deleted), `handoff` (another agent, or the same agent on another subscription) and `fork` (`context.fork {from}`, set by `POST /api/agent/threads/:id/fork`). The subscription is the agent's own sign-in, and for a model id that names its provider (`anthropic/…` in OpenCode) that provider too (`subscriptionOf`); a model without one stays on the agent's, so a model switch within it continues the session, the change applying from the next run. A fork or another subscription roots a session of its own in the queue too (`startsOwnSession`), so it neither waits for nor relinks the session it came from. A Code tab turn whose own agent has no session to resume gets a `handoff` with reason `session_gone` (`prepareCodeTurn` in `workspace/code-turn.ts`).
- **The handoff record** (`ensemble.handoff.v1`, `workspace/handoff-record.ts`): `buildHandoff` reads the earlier session's runs (back from the run continued, at most 30): their messages, reports, `Run.completion` (checks run again), `Run.packet` (acceptance criteria), changed files, the questions the person answered and an unattended run's choices, evidence, the pull request and tool use, with no model call. The record has `id` (`hof_<yyyymmdd>_<6>`), `trust: "unreviewed-data"`, `lossy` (carried, not carried), `supersedes` (the record that started the earlier session), `task` (with the packet version), `from` (agent, subscription, model requested, sent and reported, the agent's session id, run, computer, folder, branch, head), `to`, `acceptance` (`verified` only with a passing rerun, `failed`, or `unverified` with the agent's claim or a rerun that exited 0 but showed other output), `state` (worked, failed), `decisions` (cost if wrong: "Not stated" unless known), `files`, `checks`, `artifacts`, `openWork` (next step, blockers), `requests` (the owner's words), `context` (records, files to read first) and `toolProvenance`; key shapes and the run's secret values are hidden. Every bounded field is cut to fit (with "…") before the record is checked, so a long check command or a value made longer by hiding a secret never loses the record; one that cannot be made is logged and the turn goes on without it. `renderHandoff` fills at most 8,000 characters by priority (next step, acceptance, what did not work, requests, what worked, decisions, files, checks, artifacts, context, tools) and ends with the file's path. `saveHandoff` keeps it in `session_handoffs` (`SessionHandoff`: the run that got it, the run it was made from, the reason, the record); `writeHandoffFile` writes `.ensemble/handoff/<id>.md` (the rendering and the JSON) through `workspace/run-files.ts`, kept out of git in `.git/info/exclude`. On a paired computer the record is made there and sent with the run's end, and the web keeps it with its own ids (`keepCodeTurnResult`).
- Ensemble Node's nodes start and drive sessions, each node only its own ([35 §8](35_ENSEMBLE_NODE.md#8-work-on-a-computer)). A **steer** is a run that continues the one it interrupts, with `context.steer {update}` (the claim spec's `steer` on a paired computer); resuming the session, the agent gets only the change (`steerPrompt`), and with the session gone it gets the whole brief with the update in its instructions.

### 2. One folder per project: implementation reference

The person's own agents keep their sessions by working folder (Claude Code's projects, Codex's and Cursor's workspaces, Copilot's sessions by folder), so an Ensemble project gets one folder for its tasks (`workspace/agent-projects.ts`): `<workspace>/projects/<name>`. A folder alone is not a project in every agent's app, so Ensemble also files its sessions there itself (§3).

A task in a project that the person's own agent does, and that would otherwise get a new folder (no earlier task continued, no folder, repository, chat or Ensemble Node plan), works there, and the agent's app lists it with the project's other work. The folder is a git repository like a run's own; runs in it take turns (the `dir:` resource key, and the queue's same-project rule).

Session lists (the Sessions page, Continue an earlier task, `ensemble sessions`) show such a session's folder as `projects/<name>`, from the folder its computer reported for the run (the `prepared` event); a run in a folder of its own shows "its own checkout".

- The project's brief (name, summary, notes, project page, repositories, people and their roles, upcoming deliverables) is Markdown with a hash (`projectBrief`). The web server builds it when a computer claims the run (the claim's `project`, [25](25_REMOTE_TASKS_ON_YOUR_COMPUTER.md)); a local-only computer builds it from its own database. Older computers ignore it and work in a new folder.
- Before the agent starts, the brief goes into the folder's `AGENTS.md` between Ensemble's markers (the rest of the file is the folder's own), with `CLAUDE.md` and `GEMINI.md` importing it (`@AGENTS.md`), only when the hash differs from the one last written there. Those three files are kept out of the repository (`.git/info/exclude`). Runs in the folder can change them, so Ensemble never reads or writes them through a link: it reads a plain file only (`O_NOFOLLOW`) and writes a new file renamed over the old one. A continued run in the folder gets the same check (`bringProject` in `workspace/agent.ts`).
- The run's rules say it is the project's folder, that `AGENTS.md` has the brief (and, when the project changed since the folder's last run, to read it again), and to keep files only this task needs in a folder named for it. Codex, Copilot, Cursor and OpenCode read `AGENTS.md` themselves; headless Claude Code reads only the person's own settings in an Ensemble folder (a run could otherwise plant hooks for the next one), so its brief comes through the prompt's context and the rule, and `CLAUDE.md` is for the person opening the folder in the Claude app.
- Which folder is which project's, and the hash of the brief each last got, is kept in `projects/.ensemble-projects.json`, beside the folders and outside any of them, so nothing a run writes in a project folder can point Ensemble at another. A renamed project keeps its folder (and its agents' sessions); one removed is made again under its name; another project with the same name gets its short id after the name. Opening a project's task in the agent's own app ([30 §4](30_ENGINES.md#4-in-the-agents-own-app-or-a-terminal)) opens the project's folder too.
- Off with Settings → Agents → Agent sessions → *One folder per project* (`orchestration.projectFolders`). Apps' own "Projects" (claude.ai, ChatGPT) have no API an agent run can use; the working folder is what the coding agents group by.

**Sessions the person started in a project** (`projectSessions` in `workspace/outside-runs.ts`). A new task in an Ensemble project lists the sessions the person started there since the project's last Ensemble run on this computer (its newest run's end). The list goes in the brief under "Sessions <name> started in this project outside Ensemble", at most 5, newest first, each with its app, title (first message), last message and the files changed. The sources are:
- Claude Code transcripts in the folder's project (`~/.claude/projects/<folder>/`)
- Copilot sessions whose `session.start` names the folder
- the threads of the project's Codex project, found by `metadata.ensembleProjectId` or its folder; listing never makes one

Ensemble's own sessions are never listed: the ones on its runs' `engine` events and its chats' sessions. The brief says they are the person's and are not to be continued, renamed or deleted. Ensemble's clean-up deletes only the sessions its runs recorded, so it leaves these alone.

### 3. In the agents' own apps: implementation reference

An agent names a session after its first message, which for Ensemble is its instructions, and its desktop app lists only what it knows. So Ensemble does the following, best effort and never failing a turn (`workspace/engines/app-sessions.ts`):

| App | Titles | Ensemble projects | What stays out of reach |
| --- | --- | --- | --- |
| ChatGPT app (Codex) | `thread/name/set`: a chat's title, an ask's page (`Ask Ensemble: <page>`), a task's title | A Codex app-server project (`project/create`), found again by `metadata.ensembleProjectId` or by its folder and renamed with the Ensemble project; a task's new thread starts in it (`thread/start` `projectId`), as do an Ensemble Node's chats in its folder. The app's sidebar shows only the projects in its own file, `.codex-global-state.json` in Codex's home (`CODEX_HOME`, else `~/.codex`), which it reads when it starts and writes back whole while it runs. So the project goes in that file under its app-server id (`local-projects`, last in `project-order`), with the thread and the project's earlier threads (`thread-project-assignments`), only while the app is closed: no live single-instance lock in the app's data folder (`SingletonLock` on macOS and Linux, `lockfile` on Windows) and, on macOS and Windows, no app process (`codexAppOpen`, `fileCodexAppProject`). Until then it is owed in `<state>/codex-app-projects.json`, tried again every 2 minutes and when the runtime starts, and shows when the app is next opened. A thread already in a project or set apart as projectless stays where it is; the person's own project for the folder keeps its entry and gets the threads; a project renamed in the app keeps the person's name. A project removed in the app (waiting to be deleted, or gone after Ensemble filed it) is left removed: the thread starts outside it. Deleting the Ensemble project removes its Codex project once the project has been in Trash 10 minutes, so Undo finds it as it was and a project back by then keeps it (`workspace/project-delete.ts`, frame `project.delete`: [25 §4.9](25_REMOTE_TASKS_ON_YOUR_COMPUTER.md#49-subscriptions-and-included-models)). ### 4. Choosing a session: implementation reference

A new run by the person's own agent that would start a new session in a new folder (no `session`, `continueFromJobId`, folder, repository, pull request or chat; not an Ensemble Node plan or a retry) may continue one of the agent's sessions that fits the task (`workspace/session-choice/`). No model takes part: the same records always give the same decision, in milliseconds.

- **Where.** On the computer that runs the agent, when it takes the job (`createJob` in its runtime, `mayChoose`): its sessions and the text of its earlier runs are there. Ensemble on the web sends with each claim what the computer cannot know (`related`: the task's project, deliverable, meeting, parent page, labels and the tasks it names, `factsOf`; `sessionChoice`: the config, with the person's setting in `enabled`; `newSession`). A local-only computer has the records itself. The computer keeps each claimed task's facts on its run (`context.taskFacts`), so later runs are matched against it. A run claimed by an older runtime has none and is never a candidate.
- **Candidates.** This computer's sessions of the same agent that are idle, resumable, not chats, not being deleted, active in the last `limits.maxAgeDays` (30, as agents keep them), at most `limits.candidates` (20), newest first, and whose every task is of the same space and account as the new task (the web space a claim came from and whom it runs for there, `related.space` and `related.runner`; this computer's own tasks are a space of their own) and in its project, or all in none: sessions never cross spaces or projects.
- **Signals** (`Signals` in `score.ts`), for each candidate against the new task:
  - *link*: the task names a task of the session: an @mention on its page, a link in its text or the run's instructions (`ensemble://task/<id>`, `/tasks/<id>`), or a dependency;
  - *deliverable*, *meeting*, *parent page*: the same one as a task of the session;
  - *anchors*: exact things both name (`anchorsOf` in `text.ts`): file paths (a file shared by its path is not counted again by its name), code names (`rankResults`, `auth_session`, `SessionStore`), issue and pull request numbers (`#123`, `ABC-42`), web addresses. The session's side includes the files its runs changed. An anchor in more than `limits.anchorMaxDocShare` (20%) of the person's tasks, shared with more than half of the candidates, or a file every repository has (`package.json`, `README.md`, `index.ts`…) does not count;
  - *topic* (0–1): the cosine of TF-IDF vectors. Words are lower-cased, common English words and `text.extraStopwords` dropped, reduced to their stem by Porter's algorithm (ranking, ranked, ranks → rank), and each two neighbours also count as a phrase (1.5×). A term weighs (1 + ln count) × ln((N+1)/(df+1)) over the person's last `limits.corpusTasks` (2,000) tasks on this computer, so words in nearly every task weigh about nothing. The title counts 3×, labels 2×, the page, description, run reports and instructions 1×. It counts only with at least `limits.topicMinShared` (2) shared terms that are not common, and proportionally less while the person has fewer than `limits.minCorpus` (50) tasks;
  - *follow-up* or *new work*: the new task's title (`text.followUp`, `text.newWork` patterns) or labels (`text.followUpLabels`);
  - *warm*: the session was active in the last `warmMinutes` (60), so the provider's prompt cache is likely still there. Not a cut-off: a session days old is continued as readily, at the cost of the agent reading its conversation once uncached;
  - *fill*: how much of its context window the session uses, from its agent's last report (`engine_context` `used`/`size`: Claude Code's and Codex's last request, Copilot's and the ACP agents' own figure), and *tasks* in it.
- **Score** (`scoreCandidate`): the sum of weight × signal. Defaults: link 10, deliverable 3, meeting 3, parent page 2, 3 per anchor up to 6, topic × 6, follow-up +1, new work −1 (only when no link or anchor ties it), warm +1, filling more than `size.soft` (40%) −2, unknown fill and more than `size.longChainTasks` (8) tasks −2. More than `size.hard` (70%) full, or unknown fill and more than `size.hardChainTasks` (15) tasks, is too full to continue: each more task re-sends the whole conversation on every request, cached or not, and near its window the agent compacts it and loses detail.
- **Bands** (`decide`): the best score (then the most recently active) at or above `bands.confident` (6) is continued, silently: the run's card on the task page says which session and why ("Continued the agent's session: it mentions “Build the ranking API”"). When the best confident ones are too full, a new session gets the best one's last report in its instructions instead. At or above `bands.unsure` (3), and below 3, a new session, recorded with its band so near misses can be studied. Nothing asks the person: Assign → More options → *Always start a new agent session* (`Assign.newSession`, the assistant's `newSession`) skips it for a run, and Settings → Agents → Agent sessions → *Continue a fitting agent session* (`orchestration.linkedSessions`) turns it off.
- **Cost.** Bounded by the limits above: the rarity table is built from titles, labels and the first part of descriptions and pages, kept per account for `limits.corpusTtlMinutes` (60), and word matching stops at `limits.timeBudgetMs` (3 s), after which links and structure decide alone. A decision with 20 candidates takes tens to a few hundred milliseconds.
- **Tuning** (`config.ts`, `SessionChoiceConfig`). Every number and word list above is one versioned config with its defaults in code. On the web server, `ENSEMBLE_SESSION_CHOICE_CONFIG` names a JSON file with only the fields to change (for example `{"version": "2026-12-01.1", "weights": {"topic": 8}, "bands": {"confident": 7}}`); it is checked, read again within a minute of a change, and sent with every claim, so computers decide with it from their next run without a release. An invalid file is logged and the defaults apply. A local-only computer reads the same variable on itself. Change `version` with every change.
- **Records** (`SessionChoice`, table `session_choices`). Every decision: the run, task, agent, computer and project, `decision` (continue or new), `band`, the session continued or the best candidate, its score and reason, `note` (`new-session`: asked for; `too-full`; `unavailable`: the session could not take the run; `not-linked`: the web refused the session the computer named), `configVersion` and `configHash`, and every candidate's `signals`, `parts` and score, best first. When the run ends, `outcome`: its status, duration, tokens, and for a continued session whether the agent really resumed it (the agent's session id stayed the same). A computer keeps the record and sends it to the web in the web's ids (`POST /api/devices/self/jobs/:id/session-choice`, under the job's lease), which links the run to the session it continued (only one of the same account and agent on that computer). Kept for the history window (`historyRetentionDays`). To calibrate, read the rows (bands near the thresholds, `note = 'new-session'`, `outcome->>'resumed'`) and score their stored `signals` again under other weights with `scoreCandidate`: no text is needed.

### 5. Assistant chats on an AI plan: implementation reference

**One chat, one session** (`subscriptions/turn-sessions.ts`). A chat (its conversation id, the spec's `session.key`) is one session of the agent on the computer that runs it; a new chat is a new session. The computer keeps `<state>/assistant-sessions.json` (chat → agent, session id, the instructions the session was given, its folder and how many days it is kept) and a folder per chat, where the agent works and the turn's files, instructions and MCP config are kept.

**The chat's folder** (`chatFolder`). It is named after the chat, so the agents' apps, which group sessions by folder, show its name: `<state>/assistant/<title-slug>-<short id>`, the chat's title in lower-case letters, digits and hyphens (at most 40 characters, cut at a word; `chat` when none is left) and the first 8 characters of its id (an ask's: of its hash), or all of the id when another chat has that name (`chatFolderName`). The name goes in the store (`dir`) before the chat's first turn, so a turn that fails leaves no stray folder.

A chat keeps its folder while a session of it began there, its current one or one set aside to delete with the chat: Claude Code keeps a session's transcript under the folder's path (`~/.claude/projects/<folder, encoded>`), and Gemini CLI, OpenCode and Grok Build find a session by the folder it began in, as do their deletions. A chat with no session there when a turn starts takes the name of its current title, and its folder moves with it (a chat renamed before a session of it ran here, say). A chat whose session began before chats were named keeps `<state>/assistant/<key>` while it has a session, and moves to a named folder at a turn that starts with none.

A turn resumes the chat's session when the agent is the same and the chat is where that session left it (`session.position`, the chat's messages before this one that a session took part in, matches what the session's last turn left; a turn on another model or computer moves it on); it sends only the message.

A message that got no answer (its computer was offline, the turn failed before replying) and a failed exchange (the message and its error) do not count (`sessionPosition` in `assistant/agent.ts`), so a routine whose run failed while its computer slept goes on in the same session.

For an agent that keeps the instructions from a session's first message (Copilot, Cursor's agent, the ACP agents), changed instructions do not start a new session. The message is led by what changed instead (`instructionsUpdate`: "Your instructions changed since this conversation began", the lines now part of them and the lines no longer part of them). An Ensemble Node's instructions rarely change: its system prompt is its stable tier, and what changes from message to message (the room, the skills matched to the message, a new memory) leads the message as context ([35 §5.5](35_ENSEMBLE_NODE.md#55-instructions)).

When more than half of the lines changed, or after 80 messages in one session (`ROTATE_MESSAGES`), it starts a new session with the chat so far. A session replaced in the store (a new one for the same chat) is deleted from the agent at once; the chat goes on in its folder, which stays.

**A group of chats, one project folder.** A turn may name a group (`session.group {id, name}`, with `session.keepDays`): its agent then works in the group's project folder (`projectFolder` in `workspace/agent-projects.ts`, `<workspace>/projects/<name>`), so the agent's own app lists the group's sessions together, as it groups sessions by folder; the turn's own files stay in the chat's folder. An Ensemble Node's turns use the node as the group ("<Name> (Ensemble Node)") and keep a session 7 days unused ([30 §10.2](30_ENGINES.md#102-a-nodes-brain)).

Turns of one chat run one at a time; otherwise it starts one, with the chat so far (`session.history`: its newest messages, as many as fit the history budget of [11](11_HOW_THE_ASSISTANT_WORKS.md#turn-limits-and-final-answer)) before the message. A session the agent cannot reopen, or an agent too old to keep one, falls back to a new session or none, with the chat so far. Sessions unused for 30 days (or the chat's `keepDays`) are dropped and deleted from the agent.

**A session that cannot be reopened.** A Codex thread the ChatGPT app holds (§1) is waited for, every 10 seconds for up to 2 minutes (`BUSY_WAIT.chat`), and the chat shows "Waiting for the ChatGPT app…". The computer sends that line with its next batch of text (`status` on `POST …/assistant-turns/:id/stream`), so it stays in order with the reply. After the wait, or when any agent refuses to reopen a session, the chat goes on in a new session. The old session joins the chat's `retired` sessions (`forgetSession`), which are never resumed and are deleted from the agent with the chat. A session is dropped instead only when the agent said it no longer has it (`provenGone` in `workspace/engines/session-restart.ts`: Codex "no rollout found" or "thread not found", Claude Code "No conversation found", the ACP agents "Session not found").

**Why a chat restarted its session.** A turn that did not go on in the chat's earlier session of the same agent says why in its result (`restart: { reason, error }`):

| Reason | When |
| --- | --- |
| `busy` | The agent's own app held the session for the whole wait |
| `gone` | The agent refused to reopen it (`error` has what it said) |
| `instructions` | Most of Ensemble's instructions changed |
| `rotated` | The session carried `ROTATE_MESSAGES` messages |
| `moved` | The chat went on elsewhere (another model or computer) since the session's last turn |
| `expired` | The session went unused for its keeping days |

The reasons come from `lookSession` in `turn-sessions.ts` and from the turn itself. The web records `restart` in the turn's `model.call` metric and its AI-activity entry, and the computer logs a warning line. A computer before 0.8.0 sends none, and a reason the web does not know is left out.

A computer before `assistantTurns: 3` (`ASSISTANT_TURN_SESSIONS`) gets the chat so far in front of every message; a one-off completion (`complete` on a subscription: triage, a summary, a title) keeps no session, and leaves none in the agent: Claude Code runs it with `--no-session-persistence` and Codex in an ephemeral thread, while the session Copilot (named with `--session-id` from 1.0.78), Cursor's agent and the ACP agents save is deleted once the turn is over (`dropOneOff`), in the folder the turn ran in (Gemini CLI, OpenCode and Grok Build find a session by the folder it began in), which is removed after.

**A session used outside Ensemble** (`subscriptions/outside.ts`, `session-touch.ts`). The person can open an Ensemble chat's session in the agent's own app or terminal. A session Ensemble created stays Ensemble's. Nothing is watched: after each turn the computer notes how many prompts the session holds (`prompts` in the store), and before the next turn it reads the exchanges after that count:

| Agent | Where they are read |
| --- | --- |
| Claude Code (and the Claude app's Code tab) | The transcript, `~/.claude/projects/<folder>/<id>.jsonl`. Its `entrypoint` says where each prompt was typed (`claude-desktop`, `claude-desktop-3p`: the Claude app; `claude-vscode`: VS Code; `cli`: a terminal) |
| GitHub Copilot | `user.message`, `assistant.message` and `tool.execution_start` events in `~/.copilot/session-state/<id>/events.jsonl` |
| Codex | `thread/read` with `includeTurns` on Codex's app-server, before `thread/resume`; each turn is one exchange |
| Cursor and the ACP agents that reopen with `session/load` | The history the agent replays as it reopens the session (`session/update` notifications), kept apart from the turn's reply. Antigravity reopens with `session/resume`, which replays nothing |

Each exchange is the person's message, the agent's last answer, and one line for its tool calls ("Edited 2 files, ran 3 commands"); a tool's output never comes in. At most the newest 20 exchanges and 20,000 characters come in (`MAX_OUTSIDE_TURNS`, `MAX_OUTSIDE_CHARS`), each message cut to 4,000; the rest are counted (`earlier`).

They go back with the turn's result (`outside: { app, turns, earlier }`). The web saves them as the chat's messages just before the turn's message, each marked with where and when it was said (`assistant_messages.outside`: `{ app, at, earlier }`, `assistant/outside.ts`). The chat shows them as "In the Claude app". A new session gets them with the chat so far ("Said in the Claude app, outside Ensemble"). They don't count in `sessionPosition`, since the session already has them. Each import is recorded in the person's AI activity (`agent.outside`).

Then the session goes on: it is no longer retired and replaced. The count after the turn includes them, so they come in once. Cursor's agent and the ACP agents count the prompts in their replay plus the one the turn sent, where a prompt the agent left unanswered and the next one count once, as its next replay shows them (`acpPrompts`). A session that cannot be read keeps working as before. One that cannot be reopened is replaced as above, and what was read before it failed still comes in.

A message the agent took before its turn failed or was stopped is in the session all the same, so the count is noted after such a turn too (`notePromptsAfter` in `subscriptions/agents.ts`, `notePrompts` in `turn-sessions.ts`): only for the chat's current session, and without moving the chat's position. Claude Code's and Copilot's transcripts give it; Codex, Cursor's agent and the ACP agents count as they go and carry the count on what they throw (`withPrompts`). A count that cannot be made is dropped, so the next turn brings nothing in. A turn whose message never went out leaves the count as it was. The note is written after the turn's error has gone back, and the chat's next turn starts once it is. What such a turn read from the agent's app before it ran goes back with no result: it stays in the agent's session but does not come into the chat.

**Ask Ensemble: one short session per page** (`assistant/ask-sessions.ts`). An inline ask (`@ensemble` in a page, task, project, deliverable or meeting notes; `POST /api/pages/:kind/:id/ensemble`) runs on the tier in Settings → Assistant → *Ask Ensemble model* (`assistant.askTier`, Medium unless changed; the chat's default tier is separate). When that tier is an AI plan, each page has one session per person who asks there (`session.key` `ask-<kind>-<hash of person, kind and id>`, sent without `position`, so the computer resumes it however many asks came before): asking again continues it.

Asks on one page by one person are answered one after another in the order they were made (`askInLine`, taken when the request arrives; the waiting ask shows "Waiting for the answer before this one…"), never two at once and never one ahead of an earlier one. When the page's session is gone (deleted in the agent's app), the new one is given the page's earlier asks and answers of that session (`askHistory`, at most 8).

Thirty minutes after the last answer (fixed, not a setting) the session is deleted from the person's computers the way a deleted chat's is (§6): the account's pending ask sessions are kept in the preference `assistant.ask-sessions` and the scheduler's minute tick sweeps them, so a restart does not lose one; an ask that never reported back is cleared two hours after it began. The session is sent with `keepDays: 1`, so a computer that cannot delete on request yet drops it itself a day later.

An ask on a surface (`POST /api/ensemble/invoke`: Today, a board, Needs me, Code; on the chat's default tier) follows the same rules, with one session per surface and the records it is about (`anchorKey`).

### 6. Deleting and cleaning up: implementation reference

**Deleting a session** (`deleteAgentSession` in `workspace/delete-session.ts`). The person deletes a session from Ensemble Node's Sessions page, and a node asks for it with an owner-only confirmation card ([35 §8.9](35_ENSEMBLE_NODE.md#89-session-control-from-the-card)). Every computer that ran the session must be online and report `sessionDelete: 1` ([26](26_CLI.md)); otherwise nothing is hidden and the person is told which computer to connect or update. Under the session's lock its queued runs are cancelled, then each computer deletes the agent's own saved history and Ensemble marks the session deleted.

On a computer, one runtime does each deletion the web asks for (a session, a chat's session, a deleted project's Codex projects): the one that claims the request ([25 §2](25_REMOTE_TASKS_ON_YOUR_COMPUTER.md#2-pairing-and-local-state)), so two runtimes with one pairing never both do it.

Ensemble's run records, project folders and files stay. A run that continues a deleted session's runs starts a session of its own (§1).

**What goes from the agent** (`deleteNativeSession` in `workspace/engines/delete-session.ts`, used by every session deletion on this page; each agent's way in [35 §8.9](35_ENSEMBLE_NODE.md#89-session-control-from-the-card)). Only the session with that exact id is removed, and one the agent no longer has counts as deleted.

- Cursor's agent keeps a session Ensemble runs over ACP in `acp-sessions/<id>` (`store.db`, `meta.json`) and a terminal chat in `chats/<workspace>/<id>`, both in its config folder: `CURSOR_CONFIG_DIR`, else `$XDG_CONFIG_HOME/cursor`, else `~/.cursor`. Both go. A sub-agent the session started stays: Cursor keeps it as a chat of its own (`chats/<workspace>/<sub-agent id>`, whose `store.db` meta names the session in `subagentInfo.parentAgentId`), with its transcript under `projects/<workspace>/agent-transcripts/<id>/`.
- Sessions an agent starts beside its own are not deleted with it: the Claude app's side sessions and forks (their Code tab records name the parent in `spawnedFrom.sessionId` or `forkedFromSessionId`). A Codex sub-agent's thread goes with its parent's, since `thread/delete` removes a thread's descendants; Claude Code's sub-agents (`<id>/subagents/`), Copilot's (in the session's `events.jsonl`) and Gemini's (`chats/<id>/`) are part of the session's own files.
- Gemini CLI: Ensemble never runs `gemini --delete-session <id>`. When the id is not in Gemini's list for the folder it runs in, Gemini reads the id as a list number and deletes that session instead (`3d7b4ba0-…` is the third), and each start of Gemini clears its expired sessions in the background, so checking the list first does not rule that out. Ensemble removes the file under `tmp/<project>/chats/` whose recorded `sessionId` is the session's, in any project folder of `~/.gemini` or, for a run in Gemini's macOS sandbox, `~/.cache/.gemini` (`GEMINI_CLI_HOME` stands for `~` when set), with what Gemini keeps under that id: `logs/session-<id>.jsonl`, `tool-outputs/session-<id>`, the `<id>` folder and the subagents in `chats/<id>`. A session whose file name shares the id's first 8 characters stays.

**Cleaning up sessions** (`workspace/session-cleanup.ts`). The scheduler sweeps each account every 15 minutes (`orchestration.cleanSessions`, on by default): a session goes from its agent (`deleteAgentSession`, ledgered as `workspace.session.delete` by `system` with `reason: "retired"`) once every task in it is retired: deleted at least 10 minutes ago (so Undo still finds it), or done or dropped longer than the completed window and not pinned.

A session with a run still queued or going waits for the next sweep; one with a task still in use is looked at again after 6 hours, and one on a computer that is offline or too old to delete sessions after an hour (`context.sessionCleanup.nextAt` on its runs), so it never holds up the sessions behind it. A failed deletion is tried again a day later.

Each sweep reads a session once, however many of its runs match, looks at no more than 60 and deletes at most 20. Just before anything changes, under the session's lock, the deletion checks again that the session has the same runs, none of them going, and every task still retired (`guard` of `deleteAgentSession`); otherwise it leaves the session alone. Ensemble's run records, project folders and files stay.

A computer deletes the sessions of its own local tasks itself and leaves those of runs claimed from the web to the web. An assistant chat's agent session that has gone unused for 30 days is deleted from the agent too, with its folder (`subscriptions/turn-sessions.ts`).

A coding session an Ensemble Node started for itself (its task's `sourceRef` is `node:<id>`, which stays open) goes once none of its runs started or finished in 7 days (`NODE_SESSION_IDLE_DAYS`, `ENSEMBLE_NODE_SESSION_IDLE_DAYS`), with the same lock and checks; a person's own open task still keeps its session.

**Deleting a chat deletes its session** (`assistant/delete-chat.ts`, `remote/assistant-session-delete.ts`). `DELETE /api/assistant/conversations/:id` stops a reply still running, deletes the chat and its messages, then asks each of the person's computers that runs assistant turns to drop that chat's session: `dropSession` removes the store entry, deletes the session in the agent itself (`deleteNativeSession`, the delete used when a chat's session is replaced, for every subscription agent) and the chat's own folder, after any turn of that chat still running there has ended.

A computer that is away, or does not confirm, is asked again when its event stream next opens, and while it is online every 5 minutes from the scheduler's minute tick (`retryAssistantSessionDeletes`); pending requests are kept per computer in the `assistant.session-deletes` preference for 30 days (the time after which a computer drops an unused session itself), and those of a computer no longer paired are dropped. On the desktop app or CLI runtime the session is dropped directly.

Deleting a routine deletes its conversation the same way (`dropRoutineChat` in `routines/service.ts`), from the Routines page or the assistant; a routine's turns keep their session unused for twice the gap to the routine's next run, 30 to 90 days (`routineKeepDays`), so a weekly or monthly routine stays in one session.

**Deleting a project.** A project's folder and its agents' sessions stay; its Codex project in the ChatGPT app is removed once the project has been in Trash 10 minutes (§3, [25 §4.9](25_REMOTE_TASKS_ON_YOUR_COMPUTER.md#49-subscriptions-and-included-models)).
